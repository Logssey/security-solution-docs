# ADR-S002 — 유효성 검증과 6시간 재검사

- 상태: **Accepted — Java 검증 워커, 영속 작업 대기열과 6시간 재검사**, 공급자별 호출 한도는 연결 설정
- 결정일: 2026-10-09
- 기준: [PRD v0.3](../../01-requirements/PRD.md), FR-05부터 FR-09, NFR-01, SEC-04, SEC-08

## 이슈

탐지 결과는 현재 사용 가능한 인증 수단인지, 실제 업무에 쓰이는지, 어떤 리소스에 접근 가능한지를 각각 판단해야 한다. 한 API 응답으로 모두 판단할 수 없다.

## 최종 결정

유효성과 지원되는 사용 메타데이터를 기본 6시간마다 다시 확인한다. 만료 또는 폐기가 확인된 신규 발견은 기록을 보존하고 신규 사고로 올리지 않는다. 검증 불가는 사유를 기록하고 수동 검토 대상으로 남긴다. 사용 여부와 영향 범위는 별도 근거로 표시하며 조회 미지원이나 기록 부재를 미사용으로 확정하지 않는다.

## 검증 계약

발급자와 키 유형별 검증기를 사용한다. 각 시도는 결과, 사유, 검사 시각, 방법, 버전과 제한 사항을 기록한다. 미시도는 UNCHECKED, 시도 후 결론 불가는 UNKNOWN이다. 403, 404, 429, 타임아웃 등을 일괄 INVALID로 처리하지 않는다.

AWS STS, GitHub 사용자 및 설치 토큰, Notion 연결 토큰은 서로 다른 검증 계약을 갖는다. 공개 리소스 조회 성공을 인증 성공으로 오해하지 않는다. 검증을 위해 키를 갱신, 재발급, 폐기하거나 외부 데이터를 다운로드하지 않는다. 최근 시도와 마지막 성공을 분리해 기록하며 실패로 과거 성공 시각을 갱신하지 않는다.

## 실행 방식

유형별 검증기는 기존 백엔드와 같은 **Java 21** 모듈로 구현하고 대시보드 API와 분리된 워커 프로세스에서 실행한다. AWS 검증은 AWS SDK for Java 2.x, GitHub와 Notion은 승인된 엔드포인트에 제한한 Java HTTP 클라이언트를 사용한다. 공급자별 필수 구성요소, 응답 코드와 오류 본문 해석, 호출 한도는 버전 관리되는 검증기 계약으로 둔다. Python 스크립트나 Gitleaks의 검증 결과를 운영 유효성 판정자로 사용하지 않는다.

스케줄은 PostgreSQL 작업 테이블에 대상, 작업 종류, 예정 시각, 시도 번호, 상태와 멱등 키를 저장한다. Spring 스케줄러는 도래한 작업을 찾는 기동 역할만 하며 실제 예약과 재시도 상태는 DB에 남긴다. 여러 워커는 행 잠금으로 작업을 한 번씩 선점하고 만료된 실행은 복구한다. 6시간 기준 예정 시각은 마지막 성공 시각만으로 뒤로 밀지 않는다. 수동 재검증 요청은 같은 대상과 목적의 진행 중 작업을 재사용한다.

호출 제한 또는 일시 오류는 공급자별 설정 한도에서 백오프와 재시도를 적용한다. 한도에 도달하거나 기한을 넘기면 지연과 사유를 노출한다. 오류를 0건이나 INVALID로 저장하지 않는다. 설정 한도는 승인된 공급자 계약과 시험 결과로 채우며, 비어 있으면 능동 호출을 시작하지 않는다.

## 영향과 검증

- 신규 발견은 수집과 정규화가 끝나면 즉시 첫 검증 작업을 예약한다. 전체 재수집 간격과 보존 전용 무효 이력의 재검사 범위는 연결별 운영 설정으로 둔다. 유효성의 기본 6시간 주기는 유지한다.
- 공급자별 호출 제한, 백오프, 최대 재시도와 지연 허용치는 승인된 설정값과 시험 결과로 관리한다.
- 원문 미보관 시 재취득 실패가 가능하다. 이를 무효, 해결로 처리하지 않는다.
- 조치 이후 검사 전에는 이전 VALID를 최신 상태처럼 표시하지 않고 재검증 대기를 표시한다.
- 검사 트래픽도 사용 이력, 감사 로그에 영향을 줄 수 있으므로 업무 사용 여부 해석 시 검증 시각을 함께 본다.
