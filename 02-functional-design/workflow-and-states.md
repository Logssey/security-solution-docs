# 상태와 집계 규칙

기준: [PRD](../01-requirements/PRD.md). 수집부터 대응까지의 분기는 [처리 흐름](../03-architecture/processing-flow.md)에 설명한다.

## 1. 용어와 처리 단위

| 단위 | 뜻 |
|---|---|
| Source / Connection | 수집 위치와 연결 범위. GitHub 저장소, Notion 페이지, 블록, AWS 리소스, K8s 네임스페이스 등 |
| CredentialSet / key set | 함께 인증에 쓰이는 구성요소 묶음. AWS ID+Secret(+Session Token) 등. 원본 구성요소는 별도 취급 |
| Occurrence | 키가 발견된 위치 한 건. 동일 키가 여러 곳에 있으면 여러 위치를 보존 |
| Finding | 유형, 위치, 엔진, 룰, 탐지 근거를 연결한 결과 |
| ValidationAttempt | 특정 시각에 특정 검증기가 수행한 검사 결과 |
| Assessment | 영향 범위와 심각도 판정, 근거 및 정책 버전 |
| ResponseCase | 담당자, 검토, 조치, 체크리스트, 예외 이력을 관리할 대응 단위. 생성 조건은 별도 정책 |

이 이름은 논리 모델 제안이다. 물리 테이블, 최종 API 필드가 아니다. **발견 원천과 키 발급자를 구분**한다. Notion에서 AWS 키를 찾았다면 source=NOTION, credentialProvider=AWS이다.

## 2. 단위 간 관계

하나의 key set에 여러 발견 위치와 탐지 결과가 연결될 수 있다. 검증 시도, 영향 평가와 대응 이력은 시점별로 보존한다. 수집 위치와 키 발급자는 별도 속성이다. 상세 수집, 탐지, 검증 순서는 [처리 흐름](../03-architecture/processing-flow.md)을 따른다.

## 3. 상태 축

아래 enum은 기존 값을 제외하면 제안 명칭이다. API, DB 설계 시 확정한다.

| 축 | 값 | 의미 |
|---|---|---|
| 유효성 | VALID / INVALID / UNKNOWN / UNCHECKED | 유효 / 무효 확인 / 확인 불가 / 미검증 |
| 심각도 | CRITICAL / HIGH / MEDIUM / LOW, 또는 미평가 | 조치 우선순위를 위한 등급. 현재 DB는 미평가를 지원하지 않으므로 확장 필요 |
| 검토 | UNREVIEWED / REVIEWED | 담당자가 근거를 검토했는지. 기존 계약 승계 |
| 조치 | OPEN / IN_PROGRESS / REVALIDATION_PENDING / RESOLVED | 신규 및 분석 / 조치 중 / 재검증 대기 / 해결. 세부 명칭은 API 설계 시 확정 |
| 예외 | RISK_ACCEPTED 등 별도 상태, 분류 | 네 막대에서 제외하는 안을 제안. 위험 수용과 오탐, 대상 제외를 같은 의미로 쓰지 않음 |
| 최신성 | 마지막 판정 시각, 최근 시도, 조치 이후 미검증, 지연 | 키의 유효성과 독립적으로 결과가 오래됐는지 표현 |

### 유효성 사유

`EXPIRED_CONFIRMED`, `REVOKED_CONFIRMED`, `INACTIVE_CONFIRMED`, `INVALID_UNSPECIFIED`, `UNSUPPORTED_TYPE`, `INCOMPLETE_CREDENTIAL`, `SOURCE_UNAVAILABLE`, `PERMISSION_LIMITED`, `RATE_LIMITED`, `NETWORK_ERROR`, `PROVIDER_ERROR`, `VALIDATOR_AUTH_ERROR` 등을 제안한다. 공급자 응답 근거가 없으면 만료와 폐기를 추측하지 않는다.

- 미검증: 아직 검사를 수행하지 않은 상태.
- 확인 불가: 시도했으나 현재 결론을 낼 수 없는 상태.
- 무효 확인: 해당 검증 방식으로 인증 불가가 확인된 상태. 구체적 이유가 만료, 폐기인지는 별도 근거가 필요하다.
- TruffleHog `unverified`를 무효로 직접 매핑하지 않는다.

### 사고 생성 및 보존

- 만료, 폐기 확인: 이력 보존, 신규 사고 제외 — 사용자 확정.
- 검증 불가: 미해결 표시, 수동 검토 — 사용자 확정.
- 유효한 비정상 노출: 대응 대상으로 판단한다. 자동 사고 생성과 수동 승인 중 선택은 Open.
- 안전한 저장소의 정상 키 목록을 읽은 것만으로 사고를 생성하지 않는다.
- 기존 사고가 이후 무효로 바뀌어도 과거 악용, 잔여 노출까지 해결됐다고 가정하지 않는다. 종결 조건은 Open.

## 4. 4단계 조치 현황

조치 상태는 **신규 및 분석 / 조치 중 / 재검증 대기 / 해결**로 표시하고 예외는 별도로 집계한다.

신규 및 분석에서 조치 중, 재검증 대기, 해결로 진행한다. 재검증에서 잔여 위험이 확인되면 조치 중으로 돌아간다. 예외 승인과 재개는 별도 이력으로 관리한다. 키 변경은 담당자가 외부 시스템에서 수행하며 체크리스트 완료나 재검증 요청만으로 해결되지 않는다. 기존 코드의 상태값 매핑은 [구현 차이](../04-integration/current-implementation-and-gaps.md)에 둔다.

## 5. 집계 규칙

- 조치 막대, 히트맵, 미지정 목록은 **고유 CredentialSet 단위**를 기본 제안으로 둔다. 동일 키의 여러 엔진 결과, 노출 위치는 상세에서 보여준다.
- 배타적 예외 집계 제안: 같은 범위의 네 막대 합계 + 예외 수 = 조치 추적 대상 고유 키 수. 대응 단위, 대표 상태와 함께 확정한다. 제외, 보존 전용 이력이 섞이면 별도 모수 설명이 필요하다.
- 같은 키에 정상 보관 위치와 비정상 노출 위치가 함께 있을 수 있다. 위치별 노출, 조치 근거를 보존하고 한 위치의 삭제나 예외로 전체 키를 해결, 예외 처리하지 않는다. 대표 상태 계산과 대응 단위는 Open이다.
- 원문 미보관, 재취득 실패로 재검증할 수 없으면 확인 불가 사유를 남긴다. 키가 무효이거나 해결됐다는 근거로 사용하지 않는다.
- image 72의 탐지, 분류, 우선순위, 검토 완료는 **중복 가능한 진행 지표**다. 네 수의 합을 전체로 취급하지 않는다.
- image 74의 심각도×유효성 셀은 같은 기준시점의 고유 키를 센다. 미평가 심각도는 별도 수로 표시한다.
- 무효, 만료, 폐기 이력 조회와 현재 사고 집계를 분리한다. 이력 조회에 무효 키가 보인다고 신규 사고로 집계하지 않는다.
- 필터: 환경, 발견 소스, 키 발급자, 유형, 유효성, 심각도, 조치 단계, 담당자. 기존 PROD/DEV로 식별할 수 없는 소스는 임의 PROD로 넣지 않는다.

## 6. 검사 이후 조치가 일어난 경우

예시 이미지 71은 06:00 유효 판정 이후 09:05 비활성화 체크가 있다. 두 기록은 시점이 다르다. 마지막 확인 결과와 실제 조치 시각을 함께 보여주고 ‘조치 이후 재검증 대기’를 표시한다. 재검증이 실패하면 과거 성공 판정을 덮어쓰지 않고 최신 시도의 실패 사유를 추가한다.
