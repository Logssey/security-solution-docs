# PRD — Secret 탐지, 검증, 대응 관리

버전: 0.3, 작성일: 2026-10-08, 상태: 제품 요구사항 기준

## 1. 제품 목적

이 제품은 조직이 승인한 개발 및 운영 환경에서 자격 증명의 노출 가능성을 식별하고, 유효성, 접근 영향, 대응 상태를 근거와 함께 관리한다. 대상은 소스 코드에 한정되지 않는다. AWS, GitHub, Notion, Kubernetes 등에 연결된 코드 저장소, CI/CD 파이프라인, 배포 환경, 클라우드 자원, 협업 문서와 외부 서비스에서 자격 증명이 저장되거나 사용되는 위치를 다룬다. 실제로 읽을 수 있는 데이터는 연결 권한과 수집 범위에 따라 명시한다.

제품의 목표는 발견한 값을 모두 사고로 취급하는 것이 아니다. 정상적으로 보관된 자격 증명과 대응이 필요한 노출을 구분하고, 검증할 수 없는 경우에도 이유를 남겨 담당자가 조치 여부를 판단할 수 있게 한다.

### 해결할 문제

- 자격 증명은 코드, 자동화 설정, 클라우드와 외부 서비스에 서로 다른 형태로 존재한다. 발견 위치와 키 발급자를 함께 파악해야 동일한 자격 증명의 노출을 추적할 수 있다.
- 문자열 탐지만으로는 자격 증명의 완전성, 현재 유효성, 실제 사용 여부나 접근 가능한 자원을 알 수 없다. 판단 가능한 근거와 확인되지 않은 부분을 분리해야 한다.
- 키의 상태와 발견 위치는 시간에 따라 바뀐다. 검사 시각, 조치 시각, 재검증 결과를 연결해야 오래된 판정을 현재 상태로 오해하지 않는다.
- 대응에는 담당자, 조치 절차, 수행 증거와 해결 근거가 필요하다. 검토 완료나 체크리스트 완료를 위험 해소와 구분해야 한다.

## 2. 보안 기능 개요

AWS, GitHub, Notion, K8s 연결에서 승인된 데이터만 수집하고 자격 증명 후보를 분석한다. 하나의 플랫폼이 코드 저장소, CI/CD 또는 배포 환경, 외부 서비스, 키 발급자 중 여러 역할을 할 수 있으므로 플랫폼을 단일 역할로 고정하지 않는다. **발견 위치와 키 발급자를 별도로 기록**한다. 예를 들어 Notion에서 발견한 AWS 키는 발견 위치가 Notion이고 발급자는 AWS다.

| 단계 | 제공 기능 | 판단 경계 |
|---|---|---|
| 수집, 탐지 | 허용된 소스에서 룰 기반으로 후보와 위치를 찾고 수집 실패, 누락 범위를 기록 | 접근 불가를 정상 0건으로 표시하지 않음 |
| 정규화 | 키 유형과 구성요소를 식별하고 동일 자격 증명의 여러 발견 위치를 연결 | 일부 구성요소만으로 완전한 키라고 판단하지 않음 |
| 유효성 검증 | 공급자, 유형별 승인된 방법으로 검사하고 기본 6시간마다 다시 확인 | 유효성, 실제 사용 여부, 검사 최신성을 각각 표시 |
| 영향, 우선순위 | 확인된 주체, 권한, 자원, 노출 환경을 근거로 Critical/High/Medium/Low 등급을 산정 | 근거가 부족하면 미평가로 두고 침해를 추정하지 않음 |
| 대응 관리 | 담당자 지정, 절차, 체크리스트, 수동 조치 기록, 재검증, 해결 판단을 연결 | 검토 완료만으로 해결하지 않으며 키 교체, 폐기를 자동 실행하지 않음 |

상세 처리 단계와 상태, 집계 기준은 [처리 흐름과 상태](../02-functional-design/workflow-and-states.md)에 정의한다.

## 3. 적용 범위

| 구분 | 범위 |
|---|---|
| 대상 연결 | AWS, GitHub, Notion, K8s에서 승인된 저장소, CI/CD 설정, 문서, 클라우드 자원 및 클러스터 데이터를 수집 범위로 정의 |
| 초기 수집 | 연결별로 허용된 위치에서 후보 탐지, 분류, 유효성 검사, 결과 조회. K8s 내부 Secret 수집 포함 |
| 필수 목표 | 6시간 주기 재검사, 검증 불가 수동 검토, 만료, 폐기 이력 보존 |
| 필수 목표 | 영향 범위, 위험도 등급, 담당자 지정, 대응 가이드, 체크리스트, 조치 진행 표시 |
| 선택 | 근거 기반 공격 경로, 비밀 제거 정보를 이용한 AI 요약, 외부 알림 발송 |
| 제외 | AI 탐지, 자동 교체, 폐기, 재발급, 허가 범위 밖의 수집, 실제 데이터 탈취, 권한 변경을 통한 영향도 시험 |
| 구현 정책 | 원문 보관 여부와 보관 시 기간, 공급자별 검증 허용 엔드포인트, 전체 재수집 주기, 세부 권한 모델은 보안 요구사항을 충족하는 방식으로 정함 |

각 연결은 수집 위치, 콘텐츠 유형, 이력 범위, 권한과 미지원 영역을 명시한다. CI/CD 실행 로그나 아티팩트처럼 접근 범위가 별도로 필요한 데이터는 연결된 서비스에 존재한다는 이유만으로 수집 완료로 표시하지 않는다. 지원 유형의 누락, 정밀도, 재현율과 수집 커버리지를 측정하며 미탐지 0건을 보장하지 않는다.

## 4. 사용자 및 사용 시나리오

### 사용자

- 보안 담당자: 탐지 결과 검토, 영향 범위 판단, 우선순위, 예외 검토.
- 인프라, 개발 담당자: 사용처 확인, 교체 계획 수립, 외부 시스템에서 수동 조치, 재검증 요청.
- 운영 관리자: 연결 권한과 수집 범위를 관리하고 검사 상태와 실패 원인을 확인한다.

### A. GitHub 코드에서 유효한 AWS 키 발견

1. 승인된 저장소, 브랜치, 커밋 범위를 수집한다.
2. 엔진이 ID, Secret 후보를 탐지하고 위치, 룰을 기록한다.
3. 근거 있는 구성요소만 묶고 기존 동일 키와 연결한다.
4. AWS용 검증기로 현재 인증 가능 여부를 검사한다.
5. 허용된 메타데이터에서 주체와 영향 범위를 확인하고 위험도 등급을 산정한다.
6. 담당자가 상세 근거, 사용처, 절차를 확인하고 외부에서 조치한다.
7. 재검증 대기로 전환하고 검사 결과와 잔여 노출을 확인한 후 해결 여부를 검토한다.

### B. Notion 문서에서 토큰 발견, 검증 실패

호출 제한, 권한 부족, 네트워크 오류이면 UNKNOWN과 사유를 표시한다. 만료나 폐기로 판정하거나 LOW로 낮추지 않는다. 담당자가 수동 검토하거나 재검증을 요청한다.

### C. 만료 또는 폐기 확인

발견 위치와 검증 이력을 보존하고 신규 사고로 추가하지 않는다. 기존 대응 건에 과거 활성 상태나 악용 근거가 있으면 무효 판정만으로 자동 종결하지 않고 해결 근거를 확인한다.

### D. 담당자 미지정

요약 화면에서 미지정 항목을 선택한 뒤 상세 근거를 확인하고 담당자를 지정한다. 지정 이력과 대응 절차를 같은 대응 건에서 조회한다.

### E. CI/CD 설정에서 외부 서비스 토큰 발견

승인된 GitHub Actions 워크플로 파일에서 외부 서비스 토큰 후보를 발견하면 발견 위치는 CI/CD 설정으로, 발급자는 해당 외부 서비스로 기록한다. 유형별 검증이 지원되지 않으면 미지원 사유를 표시하고 수동 검토 대상으로 남긴다. 실행 로그나 아티팩트의 수집 여부는 별도 범위로 표시한다.

## 5. 기능 요구사항

다음 항목은 제품이 제공해야 하는 기능과 판정 기준이다. 공급자별 지원 범위와 필요한 권한은 명시하고, 지원하지 않는 유형이나 수집 위치는 결과에서 식별할 수 있어야 한다.

| ID | 요구사항 | 우선순위 | 수용 기준 |
|---|---|---|---|
| FR-01 | 연결, 수집 범위와 성공, 실패, 지연 표시 | 필수 | 접근 불가 소스를 0건 정상 검사로 표시하지 않고 소스, 사유, 시각을 확인할 수 있음 |
| FR-02 | 형식, 접두사, 정규식, 문맥 등 룰 기반 후보 탐지 | 필수 | 엔진과 룰 버전, 유형별 표본 결과를 기록하고 AI 탐지에 의존하지 않음 |
| FR-03 | 키 유형과 구성요소를 key set으로 정규화 | 필수 | AWS ID만 발견한 경우 Secret을 가진 완전한 자격 증명으로 표시하지 않음 |
| FR-04 | 같은 자격 증명의 여러 발견 위치와 도구 결과 연결 | 필수 | 고유 키 수와 발견 위치 수가 구분되고 원본 위치별 최초, 최근 발견 시각을 보존 |
| FR-05 | 유형별 유효성 검증 | 필수 | VALID / INVALID / UNKNOWN / UNCHECKED와 사유, 검사 시각을 조회 가능 |
| FR-06 | 유효성, 지원되는 사용 메타데이터의 6시간 주기 확인 및 수동 재검증 | 필수 | 검사 요청, 성공, 실패, 다음 예정, 지연을 추적. 사용 조회 미지원은 미확인 표시, 실패로 이전 성공 시각을 갱신하지 않음 |
| FR-07 | 사용 이력, 영향 범위 조회 | 필수 | 지원 API로 확인한 주체, 권한, 자원, 사용 시각과 미확인을 구분. 인증 성공만으로 업무 사용을 확정하지 않음 |
| FR-08 | 만료 또는 폐기 확인은 이력 보존, 신규 사고 제외 | 필수 | 만료 또는 폐기 근거가 남고 신규 사고 수에는 추가하지 않음. 원인 불명 인증 거절은 수동 검토 대상으로 표시 |
| FR-09 | 검증 불가 수동 검토 | 필수 | 미지원, 권한 제한, 호출 제한, 통신 오류, 원문 부재의 사유와 검토 대상을 표시 |
| FR-10 | 통합, 시크릿 화면에 위험도 등급과 근거 표시 | 필수 | 숫자 점수 대신 CRITICAL/HIGH/MEDIUM/LOW의 분포와 건수를 표시. 미평가를 LOW로 자동 대체하지 않음 |
| FR-11 | 위험도×유효성 매트릭스와 결과 목록 필터 | 필수 | 셀 클릭 후 목록의 필터, 집계 단위가 같음. 무효 이력과 대응 대상을 구분 |
| FR-12 | 담당자 지정과 변경 이력 | 필수 | 저장, 새로고침 후 담당자가 유지되고 변경자, 시각, 사유 추적. 팀 이름과 개인 담당자를 구분 |
| FR-13 | 4단계 조치 막대와 별도 예외 집계 | 필수 | 신규 및 분석 / 조치 중 / 재검증 대기 / 해결을 표시하고 예외는 별도로 집계. 같은 대응 건을 막대와 예외에 중복 집계하지 않음 |
| FR-14 | 절차서, 체크리스트, 교체 제안 | 필수 | 권장 조치와 실제 수행 증거가 분리되고 버튼이 키 교체, 폐기를 실행하지 않음 |
| FR-15 | 검토 완료와 위험 해소 구분 | 필수 | 검토 체크만으로 RESOLVED가 되지 않고 재검증, 해결 근거가 남음 |
| FR-16 | 공격 경로와 관련 결과 연결 | 선택 | 연결마다 근거, 확인 시각을 제공. 정책 이름만으로 데이터 접근 성공, 침해를 확정하지 않음 |
| FR-17 | AI 요약 | 선택 | 비밀 원문 제거, 전송 정책 확정 후 도입. 요약이 판정이나 조치 실행을 대신하지 않음 |

FR-07의 주체, 권한, 자원, 사용 시각은 공급자와 키 유형에 따라 조회 가능 범위가 다르다. 각 항목의 근거와 확인 시각을 표시하고 조회할 수 없는 정보는 미확인으로 남긴다.

### 출시 전 핵심 수용 기준

1. 지원 유형, 수집 범위, 미지원 영역이 문서와 화면에 명시되어 있다.
2. 같은 키를 두 도구, 여러 위치에서 발견해도 고유 키와 위치 집계가 구분된다.
3. 401, 403, 404, 429, 5xx, 네트워크 실패를 공급자, 엔드포인트별로 처리한다.
4. 유효성 검사 이후 조치한 경우 ‘조치 이후 미검증’ 표시가 남는다. 오래된 VALID를 현재 판정처럼 표시하지 않는다.
5. 만료, 폐기 확인 건은 신규 사고에 포함되지 않고 이력은 조회된다.
6. 원문 없는 키, 미지원 키, 불완전 key set이 조용히 누락되지 않고 검토 대상으로 남는다.
7. 같은 필터와 집계 단위에서 4단계 막대와 별도 예외가 중복되지 않고 대상 목록의 건수와 일치한다.
8. 담당자 지정, 검토, 조치 상태, 체크리스트는 저장되고 감사 이력이 남는다. 검토 완료와 해결은 다르다.
9. 대응 버튼을 눌러도 공급자의 키 교체, 폐기 API가 실행되지 않는다.
10. 실제 검사 시각, 범위를 표시하며 샘플, 실데이터를 구분한다.

| ID | 요구사항 | 검증 방향 |
|---|---|---|
| NFR-01 | 검사 최신성 | 유효성과 지원되는 사용 메타데이터를 기본 6시간 주기로 재확인한다. 최근 시도, 마지막 성공, 다음 예정과 지연을 구분해 표시 |
| NFR-02 | 장애, 중복 제어 | 공급자별 호출 제한, 재시도 상한, 백오프, 실행 중복 방지, 같은 결과의 멱등 적재 검증 |
| NFR-03 | 추적 가능성 | 수집→탐지→검증→평가→조치 변경을 실행 ID로 연결하고 엔진, 정책 버전 기록 |
| NFR-04 | 탐지 품질 | 정의된 평가셋의 유형, 소스, 시점별 재현율과 정밀도, 미지원 및 수집 누락을 보고 |
| NFR-05 | 화면, 집계 일관성 | 같은 환경, 소스, 기간, 단위에서 카드 수와 목록 수 일치, 로딩, 0건, 실패를 구별 |
| NFR-06 | 인터페이스 일관성 | 인증, 상태값, 시각과 집계 기준이 API와 화면에서 일치하고 기존 대시보드 사용 흐름과 연결됨 |
| NFR-07 | 운영 가능성 | 스캔 소요시간, 실패율, 검증 대기량, 지연, 검증 미지원 유형을 조회 |
| NFR-08 | 보존, 복구 | 메타데이터, 감사 이력, 증거, 원문의 보존 범위를 구분하고 각각의 삭제, 백업, 복구 정책을 정의 |

### 보안 요구사항

| ID | 요구사항 |
|---|---|
| SEC-01 | 수집용 연결 자격 증명과 발견한 키를 분리한다. 소스, 검증기별 최소 권한을 정의한다. |
| SEC-02 | 키 원문을 화면, 일반 DB 필드, 애플리케이션 로그, 오류 응답, AI 입력에 노출하지 않는다. 마스킹은 서버에서 적용한다. |
| SEC-03 | 검증용 원문은 승인된 목적에 한해 접근하고 보관하는 경우 암호화, 접근 감사, 삭제 기준을 적용한다. 도구 출력, 임시 파일, 큐, 백업에도 같은 보호 경계를 적용한다. |
| SEC-04 | 검증은 공급자, 유형별 승인된 엔드포인트에서 수행한다. 발견한 URL이나 kubeconfig의 exec 명령을 그대로 실행하지 않는다. |
| SEC-05 | 대시보드의 조회와 변경 요청에 서버 측 인증과 권한 검사를 적용한다. 담당자 변경, 예외, 검토, 재검증 요청의 수행자, 시각, 변경 내용을 감사한다. |
| SEC-06 | 전송 암호화, 저장 데이터 보호, 접근 제어, 키 관리와 비밀 제거를 적용한다. |
| SEC-07 | 수집된 코드, 문서, 도구 출력은 비신뢰 입력이다. 텍스트로 표시하고 링크, HTML, AI 입력 경계를 검증한다. |
| SEC-08 | 공급자 검증은 승인된 호출 범위와 호출량 제한을 지킨다. 검증 목적으로 실제 데이터를 다운로드하거나 외부 자격 증명과 권한을 변경하지 않는다. |

## 7. 보호 자산

제품이 노출 여부와 영향을 판단해야 하는 대상과, 제품 자체가 처리하면서 보호해야 하는 데이터를 함께 정의한다. 자격 증명이 정상 비밀 저장소에 존재한다는 사실만으로 비정상 노출이나 사고를 확정하지 않는다.

| 보호 자산 | 범위, 예시 | 필요한 보호 |
|---|---|---|
| 발견된 자격 증명, 암호화 재료 | API 토큰, 비밀번호, 개인키, AWS key set, K8s Secret의 실제 값과 구성요소 | 원문 노출 방지, 유형별 유효성, 수명주기 추적, 검증 접근 제한. 공개 식별자와 비밀 값을 구별 |
| 자격 증명으로 접근 가능한 대상 | AWS 주체, 리소스, GitHub 저장소, 조직, Notion 페이지, 워크스페이스, K8s 클러스터, 네임스페이스와 연계 시스템 | 확인된 권한, 자원, 환경을 근거로 영향 범위를 표시. 접근 성공이나 데이터 유출을 단정하지 않음 |
| 수집 대상의 코드, 문서, 설정 | 저장소 파일, 이력, Notion 문서, AWS 설정, 메타데이터, K8s Secret, 설정 | 승인된 범위와 최소 권한으로 읽고, 수집 실패, 누락, 원천 위치를 추적. 비신뢰 콘텐츠로 처리 |
| 솔루션 연결 자격 증명 | 소스 수집, 공급자 검증에 사용하는 계정, 토큰, 권한 | 발견된 비밀과 분리해 최소 권한, 접근 감사 적용. 화면, 일반 로그에 원문을 반환하지 않음 |
| 탐지, 검증, 대응 데이터 | 발견 위치, 마스킹된 근거, 동일성 식별값, 검증 시도, 결과, 심각도 근거, 담당자, 체크리스트, 감사 이력 | 무단 조회, 변경 방지, 시각, 버전, 변경자 추적, 결과의 무결성과 복구 가능성 확보 |
| 검증용 원문 및 부산물 | 재검증에 쓰일 수 있는 원문, 탐지 도구 출력, 임시 파일, 큐, 오류 로그, 백업 | 보관 여부와 관계없이 접근을 제한하고 화면, 일반 로그, AI 입력으로 전달하지 않음. 보관 시 암호화, 접근 감사, 삭제 기준 적용 |

키 유형별 비밀과 식별자 구분은 [키 종류와 수집 범위](../05-research/key-types-and-collection-scope.md)에 상세화한다. 수집 권한, 보존 기간, 원문 접근 방식의 구현 선택은 이 PRD의 보호 요건을 충족해야 한다. [아키텍처](../03-architecture/README.md), [구현 차이](../04-integration/current-implementation-and-gaps.md)는 해당 요건을 구체화하고 검증하는 문서다.
