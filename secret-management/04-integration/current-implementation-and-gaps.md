# 현재 구현과 Secret 기능 연동 차이

확인 기준: 2026-10-19. 백엔드·프런트엔드 `develop`의 V1–V10 수집·탐지·검증·조회·수동 판정·대응 건과 검토·체크리스트·외부 조치 기록, 승인 GitHub 위치 재검증·해결, 기본 안내·선택형 Groq 가이드를 기준으로 한다. 아래의 «구현»은 병합된 코드와 자동 테스트의 범위이며 모든 원천의 운영 지원이나 실제 키 폐기를 뜻하지 않는다. Groq의 실제 외부 호출은 키 미설정으로 검증하지 않았고 기본적으로 꺼져 있다. 정식 목표 계약은 [데이터 계약](../03-architecture/data-contract.md), [DB 스키마](../03-architecture/database-schema.md), [API 계약](../03-architecture/api-contract.md)에 둔다.

## 1. 문서와 구현의 경계

[대시보드 설계 문서](https://github.com/Logssey/dashboard-design-docs)는 공통 기술 스택, 로그인, 공통 화면, 통합 현황과 공통 API를 관리한다. Secret의 제품 요구사항, 수집·탐지·검증, 키 모델, 평가·대응, 상세 화면과 전용 API는 이 문서 묶음에서 관리한다. 대시보드 문서에 남았던 단일 키 테이블, 임의 등급 판정, Admin PAT Mock 상세는 Secret의 정식 설계로 채택하지 않았다.

## 2. 현재 코드와 남은 연동

| 영역 | 구현 상태 | 남은 작업 |
|---|---|---|
| 실행 경계 | API는 `POST /api/v1/secrets/runs`로 작업을 등록하고 상태를 조회한다. 서버 시작 시 외부 스캔은 수행하지 않는다. 별도 Java 워커가 예약, 작업 선점과 승인된 GitHub·AWS 범위의 수집·탐지를 실행한다. | 기존 `/credentials/scan` 직접 Notion 실행 경로의 다른 사용처를 확인하고 제거하며 Notion 수집을 워커로 옮긴다. |
| 연결·범위·작업 | V3에 연결, 승인 범위, `FULL_SCAN` 작업, 실행, 실행 범위 5개 테이블이 있다. 6시간 기본 예약, 중복 방지, 리스·재시도 실행기가 있다. 예약기와 실행기는 기본 비활성이다. V10은 `REVALIDATE` 작업과 연결 단위 활성 작업 중복 방지를 추가했다. 활성 연결은 제한된 요약으로 조회한다. 연결 테스트는 GitHub 첫 승인 저장소의 설치 토큰 권한 또는 AWS STS 계정 신원만 확인하고 스캔·연결 상태 변경을 하지 않는다. | 운영용 연결 등록·설정 편집·범위별 권한 관리와 원천별 처리기를 확장한다. 연결 테스트는 전체 승인 범위나 서비스·파일 읽기 가능성을 보장하지 않는다. 재검증 실행은 승인 GitHub 단일 범위만 지원한다. |
| GitHub 수집 | 읽기 전용 GitHub App 설치 토큰으로 승인된 저장소·브랜치·경로의 현재 커밋 파일을 읽는다. `CURRENT_COMMIT_ONLY`를 지원하고 크기·총량·깊이 제한, 부분 실패를 기록한다. GitHub 파이프라인과 작업 실행기는 둘 다 명시적으로 켜야 한다. | 승인된 이력, Actions 설정 등 추가 콘텐츠는 별도 구현·검증한다. |
| AWS IAM 메타데이터 | V6과 별도 Java 워커가 승인된 계정의 IAM 사용자 접근키 목록·상태·발급 시각·최근 사용 메타데이터를 읽는다. STS로 연결 계정을 확인하고 명시된 AWS 프로필과 범위가 일치해야 한다. 접근키 ID는 보호키 HMAC 참조와 끝 4자리 표시로 바꿔 기록한다. 발견 값은 `METADATA_ONLY`이며 탐지와 검증 단계는 `SKIPPED`다. 워커 실행과 AWS 수집은 각각 기본 비활성이다. | 루트 접근키가 있거나 확인할 수 없으면 범위 누락을 표시한다. IAM 목록에서 비밀 구성요소를 복원하거나 권한·영향을 평가하지 않는다. |
| AWS 저장소 목록 메타데이터 | 승인된 리전별 Secrets Manager `ListSecrets`, SSM `DescribeParameters`, 계정 단위 S3 `ListBuckets`의 **개수만** 수집한다. 각 범위의 완료·부분 실패·실패와 안전한 사유 코드를 V3 실행 범위에 남긴다. 계정·프로필 일치를 먼저 검사하고 다른 리전을 자동 발견하거나 읽지 않는다. 이 목록은 고유 키 인벤토리나 검증 시도를 만들지 않는다. | 이 목록 경로에서는 Secret 값, 파라미터 값, S3 객체 목록·본문 및 자원별 상세·노출 판정을 수집하지 않는다. |
| AWS 정확한 값 수집 | 별도로 승인된 단일 Secrets Manager Secret, SSM Parameter 또는 S3 객체 범위에서만 현재 값을 읽는 Java 경로가 워커에 연결됐다. `SECRET_AWS_CONTENT_READ_ENABLED`는 기본 `false`이고 AWS 수집·작업 실행 활성화, 프로필·STS 계정 일치와 `CURRENT_VALUE_ONLY` 범위를 모두 요구한다. 활성화되면 텍스트를 크기 제한과 함께 메모리에서 Gitleaks로 전달하고 안전한 탐지 결과만 저장한다. | 실계정 시험에서 Secret·Parameter 각 1건의 읽기는 성공했고 S3 후보는 `AWS_CONTENT_NON_TEXT`로 거부됐다. 안전한 UTF-8 S3 객체의 수집·탐지 완료와 운영 범위의 원문 비노출 검증은 남았다. 다른 자원으로 범위를 자동 확장하거나 외부 노출·심각도를 추정하지 않는다. |
| 탐지·정규화 | 워커가 Gitleaks 8.30.1에 승인된 GitHub 파일과 활성화된 정확한 AWS 본문을 `stdin`으로 전달한다. V4에 도구 실행, 고유 키, 발견 위치, 도구 발견 기록이 있으며 완전한 키는 보호키 HMAC으로 묶고 불완전 후보는 위치별로 분리한다. AWS 본문의 원천 참조는 자원명 대신 내부 범위 ID 기반 별칭이다. | 지원 룰과 형식을 확장하고 실제 자료 기준 품질을 검증한다. |
| 유효성 검증 | GitHub 또는 활성화된 정확한 AWS 본문에서 발견한 AWS 키 후보를 V5 검증 시도 이력에 연결한다. 같은 완전 키는 실행 주기 내 한 번만 처리한다. STS 호출 설정은 기본 `false`이며 비활성은 `UNCHECKED/DISABLED`로 기록한다. 합성 실험 저장소는 설정과 관계없이 호출을 차단하고 `UNCHECKED/SYNTHETIC_FIXTURE`로 기록한다. 이때 실행의 검증 단계는 `SKIPPED`일 수 있다. | 승인된 비합성 테스트 자격 증명과 호출 정책으로 실제 STS 분기를 검증한다. 다른 발급자 유형의 검증기는 후속이다. |
| 조회 화면 | Secret 사이드바에 `/secrets` 현황, `/secrets/findings` 탐지 목록, `/secrets/cases` 대응 관리, `/secrets/connections` 연결 관리, `/secrets/history` 스캔 이력을 둔다. 탐지 목록은 고유 키·상세와 마스킹 CSV를 제공한다. 대응 관리는 운영·`TEST` 목록, 마스킹 상세와 담당자·검토·체크리스트·외부 조치·재검증 요청·이력·해결·재조치 및 변경 이력을 표시한다. AI 안내 버튼은 기본 가이드를 조회한다. V8의 `/secrets/triage`는 연결별 `SECURITY` 권한이 있는 GitHub 위치에서만 분류·판정·건 개설을 안내한다. 연결 테스트와 스캔 이력, IAM `METADATA_ONLY` 구분도 제공한다. | 다른 호출자의 기존 `/api/v1/credentials` 사용처를 확인하고 제거한다. 연결 추가·설정 편집, 신규 키 수를 포함한 실행별 집계, 대응 요약·스냅샷은 후속이다. `REMEDIATOR`·`OPERATIONS`만 가진 사용자의 안전한 발견 근거 열람 UI도 후속이며 현행 판정 상세는 `SECURITY` 전용이다. |
| 조치 현황 | 현황 화면은 신규 및 분석 / 조치 중 / 재검증 대기 / 해결의 네 단계와 별도 예외 자리를 집계 준비 중으로 표시한다. V9 대응 건 상세는 위치별 외부 조치와 건 단계를 저장·조회한다. | `/api/v1/secrets/summary`와 실제 단계별 집계·스냅샷은 아직 없다. 인벤토리 수, 스캔 성공 수, 미평가 심각도를 조치 단계의 0건 또는 완료 건수로 바꾸지 않는다. `TEST` 건은 운영 수에 넣지 않는다. |
| 수동 판정·대응 | 미평가와 환경 `UNKNOWN`을 임의 등급이나 `PROD`로 바꾸지 않는다. V8은 연결별 `SECURITY`의 승인 GitHub 범위 `TEST`·`PRODUCTION` 분류와 위치별 `ABNORMAL`·`NORMAL` 판정을 통제된 근거·이력으로 저장한다. 합성 표본은 `TEST`만 허용한다. V7 개설 API는 최신 수동 판정과 범위 버전을 다시 확인하며 기본 목록은 시험 건을 제외한다. V9는 `SECURITY`의 확정 검토, 지정된 `REMEDIATOR`의 대응 시작·네 항목 체크리스트·위치별 외부 조치 **기록**과 버전·감사 이력을 제공한다. | 신규 발견은 `UNKNOWN`, 새 승인 범위는 `UNCLASSIFIED`로 두며 수동 판정을 재스캔으로 덮어쓰지 않는다. 판정만으로 자동 개설하거나 실제 키를 교체하지 않는다. 개설 API가 현재 위치 하나만 연결하는 제한과 심각도·영향 평가, 운영 역할 부여·오분류 교정은 후속이다. |
| 재검증·해결 | V10은 외부 조치가 기록된 승인 GitHub 위치의 비동기 재검증을 요청·조회하고, `PRESENT`는 명시적으로 재조치 단계로 돌리고 비교 가능한 `MISSING`만 보안 담당자의 해결 근거로 사용한다. 프런트엔드도 위치별 요청·결과 이력, 해결·재조치 버튼을 `capabilities`에 따라 표시한다. | AWS·Notion·K8s 및 Git 이력의 재검증, 실제 키 폐기 확인, 오탐·대상 제외·위험 수용 종결은 포함하지 않는다. |
| 대응 가이드 | 백엔드와 화면은 상태를 바꾸지 않는 기본 안내를 제공한다. 외부 Groq 호출은 기본 비활성이고 명시적 활성화·API 키·`TEST`·`Logssey/test-find-key` 합성 범위가 모두 맞을 때만 허용하며 실패 시 기본 안내로 돌아온다. | 실제 Groq 호출은 키 미설정으로 시험하지 않았다. 외부 API가 실제로 키를 폐기하거나 영향도·유효성을 판정하지 않으며 운영 사용 정책은 별도 검토가 필요하다. |
| 통합 현황 | 기존 Overview는 일반 `detection_events` 조회와 100점 카드 계약을 유지한다. Secret의 원본 기록은 전용 테이블에 있다. | 통합 조회에서 두 출처를 중복 없이 합성하고 단위·미평가·누락 범위를 명시한다. |

GitHub App을 허용된 `Logssey/test-find-key`의 `fixtures/`에만 연결한 로컬 수집·탐지 실행에서는 파일 16개를 읽고 작업이 `SUCCEEDED`로 끝났다. 합성 표본에서 고유 키·후보 9개(완전 7, 불완전 2), 위치 15개, 도구 발견 23개가 기록됐다. 표본의 긴 합성 토큰 28개가 DB 데이터 덤프와 워커 로그에 원문으로 남지 않은 것도 확인했다. 검증 연결 이후에는 별도 테스트에서 합성 저장소의 STS 차단과 안전한 `UNCHECKED` 기록을 확인했다.

분리된 개발 DB에서 AWS IAM 승인 범위를 두 차례 수동 실행했다. 두 실행 모두 `SUCCEEDED`였고 각각 접근키 메타데이터 6건을 읽었다. 재실행 후 고유 인벤토리는 6건, 관측 이력은 12건이며 모두 `METADATA_ONLY`·`UNASSESSED`·`UNCHECKED`다. 계정 요약에서 루트 접근키는 0건이었다. 이후 활성화된 17개 리전에 Secrets Manager·SSM 범위 각 17개와 전역 IAM·S3 범위 각 1개, 총 36개 범위를 승인해 실행했다. 36개 범위가 모두 `SUCCEEDED`였고 총 20개 메타데이터 항목을 세었다(IAM 접근키 6, Secrets Manager 7, SSM 1, S3 버킷 6). 확인한 AWS 자원 이름과 접근키 ID의 원문은 분리된 DB 데이터 덤프, AWS 워커 로그와 병합된 코드 차이에서 발견되지 않았다. 같은 환경에서 GitHub 수집을 다시 실행해 파일 16개를 읽고 `SUCCEEDED`로 끝난 것도 확인했다. 이 결과는 목록 메타데이터 수집 시험이며 비밀 값, AWS 자원의 내용, 키 유효성·권한·노출 상태를 확인한 결과가 아니다.

정확한 AWS 값 수집은 별도 개발 DB의 승인된 세 범위로 수동 실행했다. 이 실행은 전체 `PARTIAL`이었다. Secrets Manager 현재 Secret 값과 복호화된 SSM Parameter 값은 각각 1개 객체를 읽어 두 범위가 `SUCCEEDED`였고, 선택한 S3 객체는 `AWS_CONTENT_NON_TEXT`로 제외됐다. 시험 DB에서 Gitleaks 도구 실행 기록은 3건, 발견 기록은 0건이며 검증 단계는 `SKIPPED`였다. 이는 두 값 경로의 읽기·처리 확인이지 실제 자격 증명 탐지율이나 노출 상태의 확인은 아니다.

S3에서는 텍스트 MIME과 작은 크기에 맞는 후보 27개를 별도 메모리 조사했지만 모두 바이너리 또는 유효하지 않은 UTF-8이어서 안전한 시험 대상을 찾지 못했다. 따라서 실제 S3 UTF-8 본문의 끝까지 이어지는 수집·탐지는 검증하지 못했고 S3 운영 콘텐츠에서 발견 기록도 없다. 시험에 사용한 정확한 Secret·Parameter 값과 AWS 자격 증명 토큰을 분리된 결과 DB의 `approved_ref`를 제외한 데이터, 워커 로그와 Git 추적 파일에 대조했을 때 원문 일치 항목은 0건이었다. `approved_ref`에는 승인된 자원 식별자가 들어갈 수 있으므로 이 결과를 모든 데이터·모든 실행의 원문 비저장 보장으로 확대하지 않는다. 실제 키 유효성, 권한, 외부 노출과 심각도도 이 시험으로 판정하지 않았다.

소스 확인 위치: 백엔드의 `V3__create_secret_scheduler_tables.sql`부터 `V7__create_secret_response_assignment.sql`, `SecretRunController.java`, `SecretRunListItemResponse.java`, `SecretConnectionTestController.java`, `SecretInventoryController.java`, `SecretRunScopeResultResponse.java`, V7의 `SecretCaseController.java`·`SecretCaseService.java`·`SecretCaseRepository.java`, `secret-worker`의 `GitHubSecretJobProcessor.java`, `AwsSecretJobProcessor.java`, `AwsIamCollector.java`, `AwsMetadataCollector.java`, `AwsContentScope.java`, `AwsContentPipeline.java`, `AwsCredentialValidator.java`; 프론트의 Secret 하위 메뉴, 탐지 목록·CSV·대응 관리·연결 관리·스캔 이력 화면과 `src/api/secrets.ts`·`src/api/secretCases.ts`·`src/pages/SecretCasesPage.tsx`; 전환 대상은 기존 `CredentialListController.java`와 `NotionLeakScanService.java`다.

V8 수동 판정 확인 위치는 `V8__create_secret_manual_triage.sql`, `SecretTriageController.java`·`SecretTriageService.java`·`SecretTriageRepository.java`, 개설 조건을 강화한 `SecretCaseService.java`·`SecretCaseRepository.java`, 프런트의 `src/api/secretTriage.ts`·`SecretTriageCandidatesPage.tsx`·`SecretTriagePage.tsx`다. 기존 목록과 권한 경계 차이를 확인할 때 이 경로를 함께 본다.

V9 대응 변경 확인 위치는 `V9__create_secret_case_workflow.sql`, `SecretCaseController.java`·`SecretCaseService.java`·`SecretCaseRepository.java`와 프런트의 대응 관리 화면이다. 기본·선택형 AI 안내는 `SecretGuideController.java`·`SecretGuideService.java`에서 처리한다. V10 재검증은 `V10__create_secret_revalidation.sql`, `SecretRevalidationController.java`·`SecretRevalidationService.java`와 워커 처리 경로 및 프런트의 대응 관리 화면에서 확인한다. 이 문서의 10/15 로컬 실행 수치는 V9–V10 기능을 실계정에서 검증한 수치가 아니다.

## 3. 현재 비동기 API와 기존 API

| 경로 | 현재 계약과 경계 |
|---|---|
| POST `/api/v1/secrets/runs` | 인증된 `ADMIN`이 활성 GitHub 연결 또는 지원되는 IAM·Secrets Manager·SSM·S3 메타데이터와 단일 자원 AWS 값 범위가 있는 활성 AWS 연결의 `connectionId`와 선택적 `idempotencyKey`로 비동기 실행을 등록한다. 지원되지 않는 원천·AWS 범위는 409로 거부한다. 값 범위가 등록돼도 별도 값 읽기 설정이 꺼져 있으면 본문 API를 호출하지 않는다. `202 Accepted`, `Location` 헤더와 `{ "runId", "status" }`를 반환한다. API는 원천을 읽거나 탐지를 실행하지 않는다. 같은 멱등 키의 재요청은 기존 실행을 반환한다. |
| GET `/api/v1/secrets/runs?page={page}&size={size}` | `ADMIN`에게 실행을 요청 시각 최신순으로 페이지 조회한다. `items`, `total`, 0부터 시작하는 `page`, `size`를 반환하며 페이지 크기는 1–100(기본 20)이다. 각 항목은 실행·연결 ID, 공급자·현재 연결 표시 이름, 수동·예약 구분, 전체·단계별 상태, 범위와 완료·미완료 수, **확인한 원천 객체 수**, 요청·시작·완료 시각, 허용된 실패 코드만 제공한다. 일시중지된 연결의 과거 실행도 보인다. 객체 수를 신규 키 수로 표시하지 않는다. |
| GET `/api/v1/secrets/runs/{runId}` | `ADMIN`에게 전체·수집·탐지·검증 상태, 범위와 완료·누락 범위 수, 읽은 객체 수, 재시도 횟수, 시각, 허용된 실패 코드를 반환한다. `scopeResults`는 각 범위의 내부 ID·지원 콘텐츠 유형·리전·상태·개수·안전한 누락 코드를 제공하고 계정 ID, `approved_ref`, 자원 이름·ARN과 공급자 오류 문구는 제외한다. 작업이 대기 중이면 `PENDING`, 리스 중이면 `RUNNING`으로 표시한다. |
| GET `/api/v1/secrets` | `ADMIN`에게 고유 키 목록을 `items`, `total`, 0부터 시작하는 `page`, `size`로 반환한다. `issuer`, `componentState` 필터와 1–100개 페이지 크기를 지원한다. `METADATA_ONLY`는 값 발견과 구분한다. 최신 검증 시도가 없으면 `UNCHECKED`, 심각도는 `UNASSESSED`다. |
| GET `/api/v1/secrets/{id}` | `ADMIN`에게 마스킹된 키 요약과 개별 위치, 환경·노출·존재 상태를 반환한다. IAM 메타데이터 항목은 최신 `iamMetadata`에 키 상태, 발급·최근 사용·관측 시각, 사용 서비스·리전을 별도 반환한다. 보호키 지문과 원문은 제외한다. |
| GET `/api/v1/secrets/connections` | `ADMIN`에게 활성 승인 범위를 가진 GitHub 연결과 지원 형식의 IAM·Secrets Manager·SSM·S3 메타데이터 또는 정확한 값 범위를 가진 AWS 연결을 표시한다. 다른 원천과 지원되지 않는 AWS 범위는 선택 목록에서 제외한다. |
| POST `/api/v1/secrets/connections/{connectionId}/test` | `ADMIN`과 CSRF 검사를 거친 동기 요청이다. `CONNECTED`·`FAILED`·`UNAVAILABLE`, 안전한 사유 코드와 확인 시각만 반환한다. AWS는 승인 범위의 단일 계정과 STS 신원을 확인하고 GitHub는 첫 활성 승인 저장소의 설치 토큰·`contents:read` 권한을 확인한다. 파일·비밀 값·개별 AWS 서비스 권한은 검사하지 않으며 스캔 등록이나 연결 상태 변경도 없다. |
| GET `/api/v1/secrets/triage-candidates?page={page}&size={size}` (V8) | 현재 사용자의 연결별 `SECURITY` 권한이 있는 활성 GitHub 승인 범위의 후보 키만 페이지 조회한다. 키당 허용된 발견 위치 수, 마스킹 식별자, 발급자·유형·구성 상태를 반환한다. 기존 `ADMIN` 인벤토리 API와 권한 경계를 분리한다. |
| GET `/api/v1/secrets/triage-candidates/{secretId}` (V8) | 같은 권한 경계에서 선택 가능한 위치의 ID·연결·범위 ID, 원천 위치, 환경, 노출·존재 상태와 판정·범위 버전을 반환한다. 권한 밖 위치는 수와 상세에 포함하지 않는다. |
| GET/PATCH `/api/v1/secrets/scopes/{scopeId}/response-origin` (V8) | 연결별 `SECURITY` 권한으로 범위의 현재 구분·버전·허용 구분·분류 이력을 조회한다. PATCH는 `origin`, 허용된 `reasonCode`, `expectedVersion`을 받아 `UNCLASSIFIED`에서 한 번만 분류한다. 알려진 `test-find-key` 범위의 운영 분류는 서버가 거부한다. |
| GET `/api/v1/secrets/occurrences/{occurrenceId}/triage` (V8) | 위치별 구성·존재·노출 상태와 판정 버전, 원문 없는 Finding ID·룰·탐지 시각, 수동 판정 이력, 같은 키·구분의 `openCaseId`를 반환한다. `SECURITY` 권한이 없는 연결의 위치는 볼 수 없다. |
| POST `/api/v1/secrets/occurrences/{occurrenceId}/assessments` (V8) | `decision`, 허용된 `reasonCode`, 같은 위치의 `findingId`, `expectedVersion`으로 `ABNORMAL`·`NORMAL`을 수동 판정한다. 사유·변경 전후·수행자·시각·Finding 식별 정보를 추가 전용 이력에 저장한다. 불확실하면 `UNKNOWN`을 유지하며 키 원문·자유 메모는 받지 않는다. |
| GET `/api/v1/secrets/cases?page={page}&size={size}&origin={origin}` (V7) | 현재 대응 건의 마스킹 목록이다. 기본 `origin=PRODUCTION`, 명시적 `TEST` 조회는 별도이며 각 구분에서 키당 현재 건 하나만 센다. `{items,total,page,size}`를 반환한다. 후속 스냅샷·심각도·이력 필터는 아직 없다. |
| GET `/api/v1/secrets/cases/{caseId}` (V7–V10) | 건의 `caseOrigin`, 단계·검토 상태, 담당자, 버전, 개설·연결 위치와 담당자·검토·체크리스트·외부 조치·단계 이력, 호출자별 `capabilities`를 반환한다. V10은 위치별 재검증·재조치 가능 여부와 건의 재검증·해결·재조치 가능 여부도 제공한다. 현재 건과 해당 연결 범위에 Secret 역할이 있는 계정만 조회한다. |
| POST `/api/v1/secrets/{secretId}/cases` (V7+V8) | `{occurrenceId,reason:"ASSESSED_EXPOSURE",expectedAssessmentVersion,expectedScopeOriginVersion}`를 받는다. 서버가 최신 수동 `ABNORMAL` 판정, 분류된 범위, 두 버전, 키·존재·활성 GitHub 범위와 `SECURITY` 권한을 다시 확인해 201을 반환한다. `UNKNOWN`·`UNCLASSIFIED`와 다른 위치의 근거는 거부한다. 같은 키·구분에 현재 건이 있으면 409이며 판정만으로 건을 자동 생성하지 않는다. |
| GET `/api/v1/secrets/assignees?caseId={caseId}` (V7) | 해당 건의 모든 연결 범위에 `REMEDIATOR` 권한이 있는 기존 계정과 검증된 팀 소속만 표시한다. `SECURITY` 권한이 필요하다. |
| PATCH `/api/v1/secrets/cases/{caseId}/assignment` (V7) | 팀·개인, 허용된 사유 코드, `expectedVersion`을 받아 담당자·버전·변경 전후 이력·감사를 한 트랜잭션에 저장한다. 409 충돌, 세션·CSRF·`SECURITY` 권한 검사를 적용한다. |
| POST `/api/v1/secrets/cases/{caseId}/review` (V9) | 연결 범위의 `SECURITY`가 `CONFIRMED` 또는 `NEEDS_MORE_INFO`와 고정 사유·`expectedVersion`을 기록한다. 추가 정보 요청은 검토 완료가 아니며 조치 권한을 열지 않는다. |
| POST `/api/v1/secrets/cases/{caseId}/start` (V9) | 확정 검토 후 지정된 개인이며 해당 건의 모든 연결에 `REMEDIATOR` 권한이 있는 사람이 `OPEN`을 `IN_PROGRESS`로 전환한다. |
| PATCH `/api/v1/secrets/cases/{caseId}/checklist/{itemId}` (V9) | 지정된 `REMEDIATOR`가 `S2_V1` 네 고정 항목의 완료 여부와 제한된 증거 참조를 저장한다. 체크만으로 해결하지 않는다. |
| POST `/api/v1/secrets/cases/{caseId}/actions` (V9) | 지정된 `REMEDIATOR`가 확정 검토 뒤 발견 위치별 외부 조치 종류·실제 시각·티켓 또는 변경 참조를 기록한다. 해당 위치만 재검증 대기로 바꾸고 모든 연결 위치가 조치됐을 때 건을 대기로 바꾼다. 실제 공급자 자원은 변경하지 않는다. |
| POST `/api/v1/secrets/cases/{caseId}/guide` (선택) | 권한 있는 `SECURITY` 또는 지정된 `REMEDIATOR`에게 기본 가이드를 반환한다. TEST 합성 범위에서 명시적으로 켠 경우에만 Groq를 시도하고 오류는 기본 안내로 처리한다. DB·대응 상태를 바꾸지 않는다. |
| GET/POST `/api/v1/secrets/cases/{caseId}/revalidations` (V10) | 조치된 GitHub 위치의 비동기 재검증 요청·안전한 이력을 제공한다. 단일 승인 범위의 완전 수집과 비교 가능한 탐지가 있어야 미발견 `MISSING`을 인정한다. |
| POST `/api/v1/secrets/cases/{caseId}/revalidation-resume`·`/resolve` (V10) | `PRESENT` 위치를 추가 조치로 돌리거나, `SECURITY`가 모든 연결 위치의 조치 이후 `MISSING`을 확인해 해결한다. 타 원천·Git 이력의 잔여 노출은 검증하지 않는다. |
| GET `/api/v1/credentials` | 전환 기간의 단일 `credentials` 조회다. 정식 Secret 고유 키·위치 모델과 집계 단위가 다르다. |
| POST `/api/v1/credentials/scan` | 전환 기간에 남은 API 프로세스의 동기 Notion 스캔이다. 새 비동기 작업의 성공이나 검증 결과로 해석하지 않는다. |

인벤토리·실행·연결 API의 `ADMIN` 검사는 현재 임시 접근 경계다. V7–V9의 대응 건·담당자·검토·체크리스트·외부 조치 API와 V8의 후보·수동 판정 API는 별도 `secret_role_grants`와 연결 범위를 검사하고 `ADMIN`만으로 권한을 부여하지 않는다. 판정 후보 조회는 기존 `ADMIN` 인벤토리를 재사용하지 않으며 허용된 GitHub 위치만 SQL에서 필터한다. 대응 상세의 개설 근거 링크도 `SECURITY` 전용 판정 상세로 연결하므로 `REMEDIATOR`·`OPERATIONS`만 있는 계정의 안전한 근거 상세 열람은 후속이다. 개발용 명시적 기존 계정 역할 초기화는 제공하지만 운영 역할 관리·역할 취소 UI와 오분류 교정 API는 없다. 실행 등록·연결 테스트·대응 변경은 세션·CSRF를 사용하며 원문 자격 증명을 받지 않는다. CSV는 별도 내보내기 API가 아니라 브라우저가 같은 `issuer`·`componentState` 필터로 목록을 최대 100건씩 끝까지 조회해 만든다. UTF-8 BOM과 수식 주입 방어를 적용하고 키 원문·위치 참조를 제외한다. 총수·페이지·중복 ID 일관성 검사가 실패하면 파일 생성을 중단한다. 현재 목록 API에는 스냅샷 토큰이 없어, 동시 변경이 있어도 검사 조건을 모두 만족한 경우까지 같은 시점의 결과라고 보장하지 않는다. 새 화면은 정식 경로를 사용하고 기존 API는 다른 사용처가 없어지면 제거한다. 대시보드의 공통 인증·Overview 계약은 [공통 API 명세](https://github.com/Logssey/dashboard-design-docs/blob/main/05-api/api-spec.md)를 참조한다.

## 4. 원천별 범위와 다음 작업

- GitHub는 승인된 테스트 저장소의 현재 커밋과 파일 경로만 구현·확인했다. 워커가 없거나 관련 활성화 설정이 꺼져 있으면 등록된 작업이 자동으로 수집되지는 않는다.
- AWS 계정 전체 읽기 범위는 승인됐지만 기본 실행 범위는 IAM 접근키 메타데이터와 승인된 리전별 Secrets Manager·SSM 개수, 계정 단위 S3 버킷 개수다. 별도 `AWS_SECRETS_MANAGER_VALUE`, `AWS_SSM_PARAMETER_VALUE`, `AWS_S3_OBJECT_CONTENT`는 정확한 단일 자원을 연결에 승인하고 `CURRENT_VALUE_ONLY`와 독립된 값 읽기 설정을 켜야 한다. 개발 시험은 명시적 `new` IAM 사용자 프로필을 사용했다. 운영 설계의 읽기 전용 IAM 역할과 개발 프로필은 구분한다. `SECRET_JOB_EXECUTOR_ENABLED`, `SECRET_AWS_COLLECTION_ENABLED`, `SECRET_AWS_CONTENT_READ_ENABLED`는 각각 기본 `false`다. Secret·Parameter 실제 값 수집 성공과 S3 비텍스트 거부 범위는 위 시험 결과에 한정된다. 별도 AWS STS 검증은 발견한 완전한 키 쌍에 대한 선택 기능으로, 수집과 무관하며 기본 비활성이고 합성 실험 저장소에는 호출하지 않는다.
- Notion은 기존 API의 페이지 검색·Markdown 읽기·부분 실패 처리 코드가 있지만 워커의 승인 페이지 수집기로 아직 분리되지 않았다. 블록 전체 페이지 나눔과 지원 콘텐츠의 범위를 보완한다. Admin PAT 목록은 이번 작업에서 제외한다.
- K8s Secret 객체 수집, 공급자별 영향 평가, 통합 현황은 후속 범위다. V7–V10 대응 건·담당자·수동 판정·검토·체크리스트·외부 조치 기록·GitHub 승인 범위 재검증·해결은 `develop`에 반영됐다. 다른 원천의 재검증과 오탐·대상 제외·위험 수용 종결은 포함하지 않는다.

공유 V2 `credentials`는 유지하고 Secret 테이블 V3–V10은 백엔드 `develop`에 순서대로 병합했다. V9–V10의 대응 변경·재검증 자동 테스트는 통과했다. 아래 수치는 **10/15 당시 V8까지** 격리된 Testcontainers PostgreSQL의 백엔드·워커 테스트와 공유 로컬 개발 DB의 Flyway V1–V8 적용을 확인한 기록이다. 당시 마이그레이션 직후 기존 데이터는 자격 증명 15건, 발견 위치 21건, 실행 10건, 대응 건 0건, 범위 분류 0건, 노출 판정 0건으로 보존됐다. 이후 로컬 API에서 합성 `test-find-key`의 범위 ID 1을 `TEST`로 분류하고 위치 ID 2의 Finding ID 72를 `SIMULATED_EXPOSURE` 사유로 `ABNORMAL` 판정해 시험 대응 건 1번을 개설하고 `INITIAL_ASSIGNMENT`로 담당자를 지정했다. 확인한 목록은 `TEST` 1건, 기본 운영 `PRODUCTION` 0건이다. 이는 합성 시험 기록이며 실제 운영 키의 노출·심각도·조치 완료를 뜻하지 않는다. 브라우저 로그인 세션이 없어 화면 클릭 흐름은 검증하지 못했으며 프런트엔드 빌드와 API 흐름을 확인했다. 기존 V2 적용 이력은 파일명 변경으로 덮어쓰지 않는다. 향후 필요한 데이터 이전은 별도 계획과 검증 후 수행한다. 자세한 경계는 [마이그레이션 절](../03-architecture/database-schema.md#6-보안-보존과-마이그레이션)을 따른다.
