# 수집원과 검증기 계약

기준: [PRD](../01-requirements/PRD.md) FR-01부터 FR-09, [ADR-S001](adr/ADR-S001.md), [ADR-S002](adr/ADR-S002.md), [ADR-S006](adr/ADR-S006.md). 지원 여부는 실제 시험 결과와 별도로 관리한다.

## 1. 연결별 수집 계약

| 연결 | 초기 대상 | 범위 설정과 누락 표시 |
|---|---|---|
| GitHub | 승인된 저장소의 코드, 선택된 브랜치와 커밋 이력, 승인된 Actions 워크플로 설정 파일 | 조직, 저장소, 브랜치, 이력 범위를 연결에 명시한다. 실행 로그, 아티팩트, 저장 비밀 값은 별도 권한과 수집 범위가 없으면 미지원으로 표시한다. |
| Notion | 연결에 공유된 페이지와 지원되는 텍스트 블록 | 페이지, 하위 블록과 페이지네이션 범위를 기록한다. 공유되지 않은 페이지, 첨부 파일과 OCR은 읽지 못한 범위로 표시한다. |
| AWS | 승인된 계정과 리소스의 설정, 권한 및 지원되는 사용 메타데이터 | 계정, 리전, 서비스, 리소스 종류별로 허용 범위를 기록한다. 원문을 읽는 비밀 저장소, 객체 내용과 로그는 별도 승인 없이는 수집 완료로 표시하지 않는다. |
| K8s | 승인된 클러스터와 네임스페이스의 내부 Secret 객체 | Kubernetes API와 별도 최소 RBAC를 사용한다. projected 토큰, 외부 비밀 저장소, 노드와 etcd의 값은 Secret 객체 수집에 포함됐다고 표시하지 않는다. |

모든 연결은 콘텐츠 유형, 원천 객체 ID와 버전, 읽은 범위, 최초와 최근 성공, 부분 실패, 거부, 미지원 위치를 기록한다. 수집 대상이 0건인 정상 성공과 접근 불가로 결과가 0건인 경우를 구분한다. 승인된 원천 이외의 URL을 발견했다는 이유로 새 수집원을 자동 추가하지 않는다.

기존 Notion 페이지 읽기 코드는 공통 Java 워커가 호출하는 수집기로 정리한다. 수집기 담당 범위는 승인된 페이지, 페이지 나눔과 부분 실패 처리, 위 공통 결과 형식 및 테스트다. 수집기가 스케줄러나 대응 저장 모델을 독자적으로 정의하지 않으며 공통 DB·작업·API 계약은 구현 전에 함께 검토한다. Enterprise Admin PAT 목록 기능은 이번 수집기 정리 작업에서 제외한다. 재사용 가능한 코드와 남은 차이는 [구현 연동 현황](../04-integration/current-implementation-and-gaps.md)에 기록한다.

## 2. 탐지와 정규화

수집된 코드, 문서, 설정을 비신뢰 입력으로 처리한다. 탐지 도구의 단독 또는 병행 운영은 [ADR-S001](adr/ADR-S001.md)의 비교 결과로 정한다. 비교 단계에서는 GitHub 파일과 승인된 이력, Notion, AWS, K8s 텍스트를 수집기가 원천 객체별로 읽어 Gitleaks와 TruffleHog에 동일한 `stdin` 입력으로 전달한다. 운영 단계에는 선정한 도구 또는 조합만 실행한다. 각 입력의 원천 객체와 버전, 줄 위치는 어댑터가 도구별 결과에 연결한다. API의 크기 제한과 누락 이력은 수집 실패 또는 미지원 범위로 표시한다. 룰과 탐지기는 유형별 형식, 접두사, 정규식과 문맥을 사용하며 도구 및 설정 버전을 기록한다. 비밀 구성요소와 공개 식별자를 구별한다. 불완전한 AWS AccessKeyId나 공개 인증서만으로 완전한 인증 수단을 만들지 않는다. 동일성은 [데이터 계약](data-contract.md)에 따라 확인하고 도구별 발견 근거는 별도로 보존한다.

탐지 품질은 유형, 수집원, 시점별 합성 평가셋과 승인된 테스트 자료에서 재현율, 정밀도, 중복, 누락과 두 도구의 추가 탐지 건수로 보고한다. Gitleaks와 TruffleHog의 실행 파일 버전, 해시와 룰 또는 탐지기 설정을 각각 고정해 같은 표본에서 결과를 재현한다. 병행 운영을 선택하면 도구별 실패와 부분 누락도 별도로 기록한다. TruffleHog의 자체 검증은 평가와 운영의 탐지 실행에서 비활성화하며 어떤 도구의 결과도 공급자별 유효성 판정으로 무조건 복사하지 않는다.

## 3. 검증기 등록 계약

검증기는 발급자, 키 유형, 필수 구성요소, 승인된 호출 대상, 허용 요청, 필요한 연결 권한, 호출량 한도, 응답 해석 표와 버전을 등록한다. 허용 목록에 없는 유형이나 엔드포인트에는 네트워크 요청을 하지 않고 `UNSUPPORTED_TYPE`으로 수동 검토에 올린다. 공급자 응답의 상태 코드만으로 무효, 만료 또는 폐기를 단정하지 않는다. 실제 데이터 다운로드나 키 및 권한 변경을 검증 동작으로 등록하지 않는다.

| 유형 | 초기 검증 후보 | 구분할 결과 |
|---|---|---|
| AWS 장기, 임시 자격 증명 | 완전한 구성요소로 승인된 STS 신원 확인 | 신원 확인과 업무 리소스 접근 권한은 별개. 임시 키의 세션 토큰 누락은 불완전 |
| GitHub 사용자 계열 토큰 | 인증 사용자 확인 | 공개 API 성공이나 저장소 권한 부재를 곧바로 유효성 결과로 사용하지 않음 |
| GitHub 설치 토큰 | 설치 범위의 승인된 조회 | 사용자 토큰 검증 경로와 분리 |
| Notion 연결 토큰 | 연결 주체 확인 | 검증기 client 오류, 페이지 권한 제한과 대상 토큰 무효를 구분 |
| K8s 토큰, 개인키, 웹훅 secret, 임의 암호 | 안전한 승인 방법이 검증된 유형만 능동 검사 | 범용 API를 가정하지 않고 미지원, 불완전, 수동 검토를 표시 |

각 행은 구현 후보이며 운영 지원 선언이 아니다. 운영 지원에는 테스트 전용 자격 증명으로 성공, 명시적 무효, 권한 부족, 호출 제한, 네트워크 오류, 구성요소 누락을 구분한 기록이 필요하다. 공급자별 후보와 한계는 [검증 조사](../05-research/verification-and-risk.md)를 따른다.

## 4. 검증 결과와 실패

결과는 `VALID`, `INVALID`, `UNKNOWN`, `UNCHECKED` 중 하나와 사유, 방법, 시각, 검증기 버전을 기록한다. 시도 전 미지원 또는 원문 부재는 UNCHECKED와 사유, 시도 후 공급자 오류나 재취득 실패는 UNKNOWN과 사유로 남긴다. 만료 또는 폐기는 공급자 근거가 분명할 때만 별도 사유를 기록한다. 최근 사용 메타데이터는 신원 확인과 별도 권한, 시각 및 출처를 갖는다.

검사 성공 이후 외부 조치가 기록되면 과거 VALID를 현재 확정 상태처럼 보여주지 않고 조치 이후 재검증 대기를 표시한다. 재시도 실패는 마지막 성공 시각을 갱신하지 않는다. 스케줄과 백오프는 [보안 실행 정책](security-and-runtime.md)을 따른다.

## 5. 영향 범위 증거 계약

유효성 검증기와 영향 범위 분석기는 별도 결과를 낸다. 영향 분석기는 발급자와 토큰 유형별 매핑 버전, 확인한 권한과 적용 대상, 제한 통제, 연결의 자산 분류 버전, 증거 ID와 시각을 반환한다. [심각도 판정 정책](../02-functional-design/severity-policy.md)의 `ADMIN`, `IMPORTANT`, `LIMITED`, `MINIMAL`, `UNKNOWN` 중 하나로 정규화한다.

매핑은 지원 권한 목록과 대상 조회의 완전성을 명시한다. 조회 권한 부족, 미지원 토큰 유형, 일부 대상 누락, 상충하는 자산 분류는 모두 `UNKNOWN`과 사유를 반환한다. 인증 성공 응답이나 토큰 유형 이름만으로 권한 범주를 채우지 않는다. 새로운 공급자 매핑은 합성 사례와 승인된 테스트 계정의 권한 경계 사례를 통과한 뒤 버전을 올려 활성화한다.
