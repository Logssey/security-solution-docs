# 스캔 이력 화면과 상태 정책

기준: [PRD](../01-requirements/PRD.md), [화면 설계](dashboard-flow.md), [데이터 계약](../03-architecture/data-contract.md), [API 계약](../03-architecture/api-contract.md). 실행별 수집·탐지·검증 상태, 범위 커버리지와 화면 탐색 규칙을 정의한다.

## 1. 이 화면이 답해야 할 질문

운영자는 이력에서 **언제, 어떤 승인 범위를, 어디까지 읽었고, 무엇이 누락됐으며, 다음에 무엇을 해야 하는지** 확인한다. 작업 등록 성공은 검사의 성공이 아니다. 스캔 이력 한 행은 실행 `runId` 한 건이며, 키·발견 위치·Finding·대응 건 수와 합치지 않는다. 연결 테스트는 실행 이력에 포함하지 않는다. 위치별 재검증은 같은 실행 기록을 사용하더라도 정기·수동 **전체 스캔**과 유형·집계·행동을 구별한다. 재검증의 미발견은 그 위치의 비교 가능한 현재 승인 범위에서만 의미가 있다.

화면은 다음 사실을 따로 보여준다.

| 질문 | 표시할 사실 | 잘못된 해석 방지 |
|---|---|---|
| 작업이 어떻게 시작됐나 | 정기 전체 스캔, 수동 전체 스캔, 위치별 재검증; 요청·시작·종료 시각 | 재검증을 ‘예약 스캔’이라고 표시하지 않음 |
| 어디까지 검사했나 | 실행 당시 승인 범위의 성공·부분·실패·건너뜀·대기·진행 수와 누락 사유 | 종료된 범위를 성공 범위로 세지 않음 |
| 어떤 단계가 실행됐나 | 수집, 탐지, 유효성 검증 각각의 상태·적용 여부·미실행 사유 | 수집 성공을 키 유효성 성공으로 해석하지 않음 |
| 무엇을 확인했나 | 실제 확인한 원천 항목과, 연결 가능한 경우 해당 실행의 고유 후보·Finding 요약 | 원천 항목 수를 신규 키나 사고 수로 바꾸지 않음 |
| 다음 행동은 무엇인가 | 권한·설정 수정, 일시 오류 재시도, 탐지 결과 확인, 대응 건의 위치별 재검증 확인 | 실패·근거 부족을 ‘발견 0건’ 또는 ‘해결’로 표현하지 않음 |

### 다른 화면과 연결할 신뢰 정보

현황의 `검사 누락`과 키·위치의 최신성 경고는 실행 이력의 같은 범위 근거를 사용한다. 마지막 성공 실행과 최근 시도는 별도 ID·시각·승인 범위 버전을 가진다. 최근 시도가 실패하면 과거의 마지막 성공은 보존하되 현재도 확인됐다고 표현하지 않는다. 승인 범위가 추가·변경돼 과거 성공과 비교할 수 없으면 새 버전의 `검사 전` 또는 `비교 불가`로 표시한다. 아직 실행하지 않은 범위와 실행했지만 실패한 범위를 모두 ‘실패’로 합치지 않는다.

키 상세에서 `검사 누락`을 열면 해당 위치에 실제 적용되는 범위와 실행 상세로 이동하고, 실행 상세에서 결과를 열면 해당 실행에 연결된 값 후보·위치만 조회한다. 권한 있는 범위에 대해서만 관계를 제공하고 제한된 범위의 이름·정확한 수·원천 참조는 링크나 집계에 넣지 않는다. 범위 실패는 확인된 ABNORMAL 판정·대응 건을 지우지 않고 신뢰 범위 경고와 복구 작업을 추가한다.

검사 누락과 기한 지연도 다르다. 예약 시각이 지났으나 실행이 아직 등록되지 않았거나 실행기가 꺼진 경우는 `검사 지연`과 안전한 설정 사유로 설명한다. 조회 오류 때문에 최신 실행을 받지 못한 경우는 `현황 조회 실패`이지 새 검사 실패가 아니다. 어느 경우에도 과거 성공을 최신 정상 상태로 재사용하지 않는다.

## 2. 주소와 이동

목록은 `/secrets/history`, 상세는 `/secrets/history/:runId` 독립 주소다. 목록의 행 제목과 ‘상세 보기’는 같은 상세 주소로 이동한다. 상세는 목록 아래 또는 페이지 끝에 추가하지 않는다. 실행 ID는 URL에서 양의 정수인지 먼저 검사한다. 직접 입력한 주소도 새로고침·공유·뒤로 가기 후 같은 실행을 열며 사용자 권한은 서버가 다시 확인한다.

목록 조건은 URL의 `page`(화면 1부터 시작), `type`(`SCHEDULED|MANUAL|REVALIDATION|ALL`), `status`, `connectionId`, `provider`(수집 플랫폼), `from`, `to`, `snapshotId`로 보존한다. 같은 HISTORY 스냅샷의 후속 페이지에 같은 정규화 필터를 사용하고 WORKBENCH·INVENTORY 스냅샷으로 바꾸어 조회하지 않는다. 기본 정렬은 요청 시각 내림차순, 동률일 때 `runId` 내림차순이다. 필터를 바꾸면 `page=1`로 돌리고 다른 조건은 유지한다. 상세로 이동할 때 이 목록 조건을 허용된 쿼리로 전달한다. ‘이력으로 돌아가기’는 같은 조건과 페이지를 열고 선택 행으로 스크롤·키보드 포커스를 복원한다. 직접 상세 URL로 들어와 복귀 맥락이 없으면 기본 목록으로 간다. 브라우저 뒤로 가기도 같은 결과를 낸다. 상세 진입 직후에는 상세 제목에 포커스를 옮기고, 화면은 맨 위부터 읽힌다.

상세에서 발견 결과로 이동할 때는 `runId`를 서버 조회 필터로 전달하고, 같은 실행·권한 범위의 결과만 보여준다. 위치별 재검증은 권한이 있는 경우 해당 대응 건과 위치로 돌아가는 링크를 제공한다. 재검사 이력의 canViewRun=false이면 위치 결과만 표시하고 연결 운영 정보를 포함한 실행 상세 링크는 제공하지 않는다.

## 3. 목록에서 즉시 읽을 정보

목록 위에는 현재 필터와 기준시각을 명확히 표시한다. 상단 집계가 있다면 **서버가 동일 필터에 대해 계산한 전체 결과**만 사용하고 `전체 실행`, `정상 종료`, `부분·실패`, `진행 중`을 유형별로 나눈다. 현재 페이지 20행만 세어 전체 통계처럼 보이지 않게 한다. 집계를 신뢰할 수 없으면 확인 불가 상태를 표시하고 추정한 숫자를 만들지 않는다. 정기·수동 전체 스캔의 성공률에 위치별 재검증을 넣지 않는다. 이전 성공과 최근 실패가 동시에 있으면 마지막 성공 시각과 최근 시도 시각을 함께 표시한다.

| 열 | 표시 |
|---|---|
| 실행 | `SCAN-{runId}` 또는 재검증임을 알 수 있는 안전한 식별자와 정기·수동·재검증 유형 |
| 연결 | 공급자와 허용된 연결 표시 이름. 표시 이름이 바뀌었다면 과거 사실로 표시하지 않고 안전한 연결 #ID를 사용. 범위 별칭은 실행 당시 스냅샷을 유지 |
| 상태 | `대기`, `진행 중`, `정상 종료`, `부분 실패`, `실패`, `취소`와 핵심 누락 사유. 색상만으로 의미를 전달하지 않음 |
| 범위 커버리지 | `성공 n / 전체 m`과 `부분 p·실패 f·건너뜀 s`를 분리. 진행 중이면 대기·진행 범위 수를 표시 |
| 수집 항목 | 실제 확인한 원천 항목 수. 누락이 있으면 ‘n개 확인 · 일부 범위 미확인’; 모든 범위가 실패했으면 `확인 불가` |
| 시각 | 요청, 시작, 종료 중 현재 상태에 맞는 대표 시각과 KST 표시. 소요 시간은 시작·종료가 모두 있을 때만 계산 |
| 다음 행동 | `상세 보기`; 권한·설정 실패면 상세에서 연결 관리로, 부분 실패면 누락 범위로 바로 이동 |

서버는 권한과 모든 필터를 적용한 뒤 페이지를 자르고 동일 조건의 `total`을 반환한다. 필터 결과 0건은 ‘조건에 맞는 실행 없음’, 연결 미설정은 ‘검사 가능한 연결 없음’, 조회 실패는 별도 오류로 표시한다. 아직 검사되지 않은 승인 범위를 0건 성공으로 표시하지 않는다. `from`·`to`는 UTC 경계로 질의하고 KST 화면 표시는 별개이며, 날짜 범위가 잘못되면 사용자가 수정할 수 있게 안내한다.

## 4. 배타적 범위 상태와 단계 상태

실행 등록 시점의 활성 승인 범위를 범위 버전과 함께 고정하고, 화면의 `scopeCount`는 그 실행에 속한 `secret_run_scopes` 수다. 범위 수는 새 실행의 여섯 처리 상태로 배타적으로 집계한다. API는 호환용 CANCELLED와 근거가 없는 UNKNOWN 키도 반환한다. 이 값이 있으면 여섯 상태의 합만으로 전체 검사 성공을 주장하지 않는다.

범위 스냅샷은 실제 실행 목적을 따른다. 정기·수동 전체 스캔은 그때 승인된 적용 범위, 위치별 재검증은 해당 위치의 승인된 비교 범위를 고정한다. 재검증 성공으로 검사하지 않은 나머지 연결 범위까지 성공으로 갱신하지 않는다. 실행 이후 범위가 추가되면 그 새 범위는 과거 실행의 분모에 소급 추가하지 않으며, 현재 현황에서는 새 버전의 검사 전 사실로 별도 표시한다. 승인 철회·권한 변경으로 실행 중 범위를 더 읽을 수 없으면 과거 승인 스냅샷이 계속 읽을 권한을 부여하는 것은 아니며 읽기를 중단하고 사유를 남긴다.

```text
scopeCount = pendingScopeCount + runningScopeCount + successfulScopeCount
           + partialScopeCount + failedScopeCount + skippedScopeCount + unknownScopeCount + cancelledScopeCount
finishedScopeCount = successfulScopeCount + partialScopeCount + failedScopeCount + skippedScopeCount + cancelledScopeCount
gapScopeCount = partialScopeCount + failedScopeCount + skippedScopeCount + cancelledScopeCount
unverifiedScopeCount = scopeCount - successfulScopeCount
```

`gapScopeCount`는 종료 후 확인된 누락이며 `unverifiedScopeCount`는 대기·진행 중인 범위까지 포함한 아직 성공으로 확인되지 않은 수다. 진행 중에는 두 값을 같은 실패 수로 표시하지 않는다.

여섯 값은 단순 `collectionStatus`가 아니라 범위의 **필수 적용 단계가 어디까지 끝났는지**를 나타내는 `scopeOutcome`이다. 수집이 완전해도 그 범위에서 필수 탐지가 실패하면 `SUCCEEDED`가 아니라 `PARTIAL`이다. 수집 자체가 실패하면 `FAILED`, 승인 범위가 미지원·비활성이어서 시작하지 못하면 사유 있는 `SKIPPED`다. 메타데이터만 읽는 범위에서는 탐지·검증이 `NOT_APPLICABLE_METADATA`로 건너뛰어도 수집이 완전하면 범위 결과는 `SUCCEEDED`일 수 있지만 화면은 **키 값 미검사**를 함께 표시한다. 자격 증명 검증이 선택 설정으로 꺼져 있거나 유형 미지원이면 범위 결과의 성공과 별도로 `UNCHECKED`·미검증 사유를 표시한다. 켜기로 승인된 필수 검증이 실패하면 범위 결과를 `PARTIAL`로 남긴다. 과거 데이터에서 단계별 적용 여부를 복원할 수 없다면 성공 수를 추정하지 않고 집계 확인 불가로 표시한다.

`SUCCEEDED` 범위의 `objectCount=0`만 그 범위에서 정상적으로 확인한 항목이 0개라는 뜻이다. `PARTIAL`은 확인한 부분과 확인하지 못한 부분이 공존한다. `FAILED`·`SKIPPED`는 수집을 완전하게 끝내지 못한 범위이므로 항목 수가 `0`이어도 ‘비밀이 없음’이 아니다. `PENDING`·`RUNNING`은 아직 최종 집계에서 성공·실패로 해석하지 않는다. 범위별 `objectCount`는 원천 항목 수이며 중복 제거한 키 수가 아니다. 확인한 수의 합계가 있더라도 누락 범위가 있으면 ‘총 대상 n개’라고 말하지 않는다.

실행 결과 `CANCELLED`는 취소·중단된 작업이며 성공·실패와 별도다. `secret_jobs.status=CANCELLED`인 작업은 아직 시작 전이든 일부 범위를 처리했든 대응 `secret_scan_runs.result_status=CANCELLED`로 확정한다. 이미 끝난 범위 결과는 보존하고 시작하지 못한 범위는 `SKIPPED`·`JOB_CANCELLED`, 시작했으나 완료하지 못한 범위는 `FAILED`·`JOB_CANCELLED`로 확정한다. `FAILED` 또는 `CANCELLED`로 종료될 때 남은 `PENDING`·`RUNNING` 범위를 그대로 ‘검사 진행 중’처럼 보이지 않게 한다. 과거 데이터에서 이 정리가 빠졌다면 화면은 그 수를 ‘미처리 범위’로 따로 드러내고 전체 커버리지를 성공으로 표시하지 않는다. 종료 후의 빈 범위 목록도 `0개 검사 성공`과 다르다. 과거 실행의 확정 결과는 해당 시점의 근거 없이 소급 변환하지 않는다.

종료 범위에는 성공·부분 실패·실패·건너뜀이 모두 포함된다. 종료 범위 수를 성공 수로 표시하거나 종료 수와 누락 수를 배타적인 쌍처럼 더하지 않는다. 상태 근거가 불완전하면 임의 보정값 대신 ‘집계 확인 불가’를 표시한다.

수집·탐지·검증은 범위 수와 다른 **단계 축**이다. 단계마다 `status`, `required`, 안전한 `reasonCode`, `observedAt`을 제공한다. required는 적용 요구 여부의 boolean이고 실행 근거 자체를 뜻하지 않는다. status=UNKNOWN 또는 EVIDENCE_NOT_RECORDED·STAGE_NOT_RECORDED 사유가 있으면 과거 적용/실행을 추정하지 않는다. 메타데이터 목록만 수집한 실행에서 탐지·검증 `SKIPPED`는 `NOT_APPLICABLE_METADATA`처럼 해당 단계가 대상이 아님을 명확히 표시한다. 기능 비활성, 지원되지 않는 유형, 권한 부족, 작업 실패는 각각 다른 사유다. `SKIPPED`를 성공·유효·무효로 해석하지 않는다. 전체 실행의 `SUCCEEDED`는 적용 대상 단계가 정의된 범위에서 끝났다는 뜻이지 모든 자격 증명이 유효성 검증됐거나 안전하다는 뜻이 아니다. 단계 결과와 개별 키의 `VALID|INVALID|UNKNOWN|UNCHECKED`는 분리한다.

## 5. 독립 상세 화면

상단에는 실행 ID, 실행 유형, 공급자·안전한 연결 이름, 전체 결과, 요청·시작·종료 시각, 재시도 횟수와 마지막 오류를 한 번에 보이게 한다. 바로 아래 **지금 확인할 일**에 확인된 누락의 수·대표 사유와 다음 행동을 표시한다. 본문은 `범위 커버리지`, `수집·탐지·검증`, `이번 실행의 발견 결과`, `기술 기록` 순서다. 길이가 긴 범위 결과와 기술 기록은 별도 영역에서 펼치되, 핵심 오류와 다음 행동은 접지 않는다. 상세를 읽으려 목록의 끝까지 스크롤할 필요가 없어야 한다.

범위 표는 성공·부분·실패·건너뜀을 우선으로 묶고, 필요하면 범위 유형·리전·상태로 필터한다. 각 행은 안전한 표시 별칭, `범위 #{scopeId}`, 콘텐츠 유형, 리전, 수집 상태, 확인 항목 수 또는 `확인 불가`, 사람이 이해할 수 있는 누락 사유와 코드, 마지막 시각을 제공한다. 같은 유형·리전의 승인 범위가 여러 개면 scopeId와 runScopeId를 구별하고 현재 승인 범위는 `범위 #{scopeId}`로 식별한다. `approved_ref`, 저장소 경로, AWS 계정 번호, 자원 이름·ARN, 키 원문, 공급자 오류 본문을 일반 응답·화면에 넣지 않는다. 표시 별칭은 승인 시 별도로 검토한 값만 쓰며 보호된 참조에서 자동으로 만들지 않는다. 권한에 따라 별칭을 표시할 수 없으면 유형·리전·내부 범위 번호만 쓴다. 과거 실행의 범위 별칭은 당시 안전한 스냅샷을 사용한다. 연결은 안전한 내부 번호로 식별하고 현재 원문 이름을 과거 표시 스냅샷이라고 주장하지 않는다.

결과 영역은 같은 실행에 귀속된 `Finding` 수, 고유 키 후보 수, 새 후보 수를 각각 **단위와 근거가 있는 경우에만** 표시한다. 후보 목록 링크는 `runId` 필터와 권한을 서버에서 다시 검증한다. 한 키에서 여러 엔진 Finding이 나왔다고 키 수를 늘리지 않는다. 실행과 발견 결과의 연결 근거를 확인할 수 없으면 `결과 확인 불가`로 표시하고 `0개`라고 쓰지 않는다. 수집 또는 탐지가 실패해 누락이 있으면 ‘확인된 범위에서 n개, 나머지는 확인 불가’로 표시한다. 키 유효성·외부 노출·심각도는 이 실행의 후보 수에서 추론하지 않는다. 재검증 실행은 결과의 `PRESENT|MISSING|UNKNOWN`과 비교 가능한 범위·탐지 버전 여부를 대응 건의 위치별 근거로 보여주고 일반 새 키 수 카드와 분리한다.

위치 화면의 대표 표현은 `현재 발견`, `재검사에서 미발견`, `검사 후 확인 불가`처럼 범위를 명시한다. 일반 전체 스캔에서 문자열이 나오지 않았더라도 해당 위치의 조치 이후 완전한 비교 범위와 탐지 조건을 증명하지 못하면 해결용 MISSING으로 승격하지 않는다. 테스트 출처 실행의 결과는 출처 표시를 유지하며 운영 사고·해결 건수에 합산하지 않는다. 시험 출처에서 발생한 실키 의심 경고는 실행 성공 여부와 별개의 사실로 연결한다.

`newCredentialCount`는 이 실행에서 **처음 생성된 고유 CredentialSet** 중 해당 실행의 값 후보 Finding과 연결된 수다. 서버는 최초 생성 실행 ID를 동일성 키의 원자적 삽입 시점에 기록하고, 같은 실행의 여러 Finding·위치를 한 번만 센다. 이전에 본 키가 새 위치에 나타난 수는 ‘신규 후보’가 아니라 별도 위치 변화다. `CANDIDATE`가 나중에 `CONFIRMED`로 승격돼도 동일한 항목이라면 처음 발견한 실행에만 센다. 정규화로 새로운 동일성 항목이 생긴 경우에만 그 실행에서 신규 후보로 세며 과거 불완전 후보와 동일 키였다고 소급 주장하지 않는다. 메타데이터만 수집한 범위와 재검증 실행은 새 값 후보 수 집계 대상이 아니다. 과거 실행에 최초 생성 실행을 신뢰할 수 있게 복원할 근거가 없거나 결과 연결이 없으면 `null`과 ‘집계 확인 불가’를 반환·표시하고 `0`을 만들지 않는다. 부분 실패에서 제공 가능한 수는 ‘확인된 범위의 신규 후보 n개’로 한정한다.

실행 중에는 서버 응답에 따라 상태를 갱신하되 종료 뒤 자동 조회를 멈춘다. `PENDING`은 다음 실행 가능 시각과 실행기 비활성 사유가 제공될 때만 보여준다. 진행 중 `0 / m`은 아직 결과가 없는 상태이지 정상 0건이 아니다. 필요한 수동 전체 검사는 기존 실행을 수정하지 않고 승인 연결의 새 실행 ID를 만든다. 자동 재시도 횟수와 위치별 재검증을 구별하고, 증명할 수 없는 이전/새 실행 관계를 임의 링크로 만들지 않는다. 권한·설정 오류면 새 검사 버튼보다 연결 관리의 해당 연결로 안내하고, 일시 오류라면 승인 범위 재검사를 제안한다. 재검증의 재시도는 일반 전체 스캔이 아니라 해당 대응 건의 위치별 재검증 절차로 돌려보낸다.

## 6. 실패·권한·접근성

| 상황 | 화면 행동 |
|---|---|
| 목록 또는 상세 로딩 | 해당 영역에 로딩 상태를 표시하고 기존 성공 자료를 새 실행 결과처럼 재사용하지 않음 |
| `403` | 접근 권한이 없음을 말하고 허용된 상위 목록으로 이동. 상세 존재·자원 이름을 추측할 단서 제공 금지 |
| `404` 또는 삭제된 실행 | 실행을 찾을 수 없음을 말하고 목록으로 이동. 목록 전체를 오류로 바꾸지 않음 |
| 일시적인 조회 실패 | 안전한 일반 오류와 ‘다시 조회’를 같은 영역에 표시. 과거 성공 결과를 최신 결과로 바꾸지 않음 |
| 부분 실패 | 실패한 범위와 사유를 상단과 범위 표 양쪽에서 확인 가능하게 표시. 성공 범위의 발견만 별도 표시 |
| 검사 대상 또는 단계 미지원 | 미지원/해당 없음 이유를 표시하고 성공·안전·0건으로 바꾸지 않음 |
| 700px 이하 화면 | 요약·단계·범위 결과를 한 열로 배치하고 긴 범위 표는 열 제목을 유지한 채 가로 스크롤. 하단에 상세를 붙이지 않음 |

상태 배지에는 색 외에 텍스트와 사유를 사용한다. 표 행과 링크는 키보드로 열 수 있고 포커스가 보인다. 자동 갱신은 화면의 스크롤·포커스를 빼앗지 않고, 상태 변화는 적절한 알림 영역에서만 읽힌다. 날짜는 API의 UTC 값을 KST로 변환해 표시하되 시간대를 명시한다. 외부 원천 링크는 서버가 확인한 허용 경로와 해당 사용자의 원천 접근 권한이 있는 경우에만 제공한다.

## 7. 수용 시나리오

1. 12개 범위가 모두 `SUCCEEDED`이고 탐지 결과가 0개면 ‘성공 12/12, 확인된 범위의 후보 0개’를 보여주되 ‘안전한 키 0개’라고 표현하지 않는다.
2. 12개 중 7개 성공·1개 부분·4개 실패면 성공 7/12, 누락 5/12와 안전한 사유를 보여준다. 종료 범위가 12개라는 이유로 ‘12개 성공’으로 표시하지 않는다.
3. IAM 메타데이터만 성공해 탐지·검증이 해당 없음이면 전체 수집 성공과 ‘키 값 미검사·유효성 미판정’을 함께 보여준다.
4. 실패한 실행에서 확인 항목 수가 0이면 ‘확인 불가’로 표시한다. 재검사 후 새 실행 ID와 이전 실행을 구별한다.
5. `REVALIDATION` 실행은 ‘위치별 재검증’으로 표시하고, 권한 있는 대응 건의 위치로 연결한다. 정기 전체 스캔의 성공률에 합산하지 않는다.
6. 목록의 3페이지에서 상세를 열고 돌아오면 필터·3페이지·선택 행과 키보드 포커스가 복원된다. 직접 상세 링크를 열면 기본 목록으로 돌아간다.
7. 직접 상세 주소로 접근해도 동일한 권한 검사를 적용한다. 존재하지 않거나 권한 없는 실행은 보호된 오류 화면을 보여준다.
8. 같은 유형·리전의 AWS 값 범위가 여러 개여도 안전한 범위 번호로 구분하고 보호된 승인 참조·자원 이름·원문은 화면·URL·일반 로그에 나오지 않는다.
9. 부분 실패 후 후보가 보이더라도 누락 범위를 정상 0건으로 집계하지 않는다. 목록·상세·현황의 실행 상태와 시각이 일치한다.
10. 마지막 성공이 06:00이고 최근 시도 12:00이 실패하면 두 시각·실행을 구별한다. 키·위치에는 마지막 발견과 확인 불가 경고가 함께 남고 MISSING으로 바뀌지 않는다.
11. 12개 범위의 전체 스캔 성공 뒤 새 승인 범위가 추가되면 과거 실행은 12/12로 유지되고 현재 현황은 새 범위가 검사 전임을 표시한다. 한 위치의 재검증 성공은 13개 전체 범위의 성공으로 집계되지 않는다.
12. 실행기가 비활성인 검사 지연, 실행 중 원천 권한 실패, 화면 조회 장애가 서로 다른 이유·다음 행동으로 표시된다. 어느 오류도 발견 0개·해결 완료로 보이지 않는다.
