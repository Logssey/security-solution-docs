# 대응 단위와 상태 전이

기준: [PRD](../01-requirements/PRD.md), [후보 판정과 조사 대기열](triage-policy.md), [상태와 집계](workflow-and-states.md), [ADR-S003](../03-architecture/adr/ADR-S003.md), [ADR-S004](../03-architecture/adr/ADR-S004.md), [ADR-S008](../03-architecture/adr/ADR-S008.md)

이 문서의 **목표 정책**은 보안 담당자가 확인한 근거를 한 번 기록하면 조치 담당자에게 실제 할 일이 전달되고, 조치 뒤 확인한 범위와 남은 불확실성을 구분할 수 있게 하는 것이다. 아래 `현행` 표시는 V7–V12 구현의 전환 경계이며 목표 기능이 이미 제공된다는 뜻이 아니다. 키 원문은 판정·조치 요청과 화면에 넣지 않는다.

## 1. 처리 단위와 범위

CredentialSet은 동일한 인증 수단의 구성요소를 묶는다. 동일성을 증명할 수 없는 불완전 후보는 접두사나 마스킹 문자열이 같아도 합치지 않는다. Occurrence는 원천 객체와 버전을 포함한 발견 위치다. 여러 엔진이 같은 키와 위치를 찾으면 각 Finding은 보존하되 위치는 한 번만 센다. 같은 키의 정상 보관 위치와 비정상 노출 위치는 함께 보일 수 있지만 판정과 조치는 위치마다 독립적이다.

ResponseCase는 한 CredentialSet의 **확인된 비정상 노출**을 조정하는 단위다. 같은 운영·시험 구분 안에서 현재 건은 키당 최대 하나다. `TEST`는 별도 시뮬레이션 범위이며 같은 키의 `PRODUCTION` 건과 합치거나 운영 사고 수에 넣지 않는다. 현재 건에는 같은 키·같은 구분의 확인된 비정상 노출 위치를 모두 연결하고, 위치마다 담당자, 조치, 재확인과 제한 사항을 기록한다. 정상 인벤토리, 오탐, 검토 대기 후보와 탐지 도구 Finding 자체는 대응 건 수에 넣지 않는다. 해결 후 새 노출이 확인되면 이전 건을 보존하고 새 건을 연다.

### 승인 범위의 대응 구분

수집을 승인한 사실은 그 위치에 평문 키 보관을 허용했다는 뜻이 아니다. `TEST`·`PRODUCTION` 구분은 연결의 범위를 승인할 때 대상의 사용 목적, 소유자, 근거 참조, 승인자, 유효 기간과 범위 버전으로 정한다. 운영 여부를 저장소 이름, 키 종류, 환경 `PROD`·`DEV`·`UNKNOWN`에서 추정하지 않는다. 합성 시험 자료는 `TEST`만 허용한다. 하나의 승인 범위에 시험 자료와 운영 자료가 섞이면 서로 다른 하위 범위로 분리하고, 분리 전의 `UNCLASSIFIED` 위치는 운영·시험 어느 집계에도 넣지 않은 채 분류 대기열에 둔다. 새 연결이거나 기존 미분류 범위는 보안 담당자가 분류를 확인하기 전에는 대응 건을 열지 않는다.

운영 관리자는 범위와 근거를 제안하고 해당 연결의 `SECURITY` 권한자가 구분을 확정한다. 분류 이력은 추가 전용으로 남긴다. 오분류는 기존 값을 조용히 덮지 않는다. 교정 요청에서 이전·새 구분, 사유, 영향받는 위치·대응 건과 수행자를 보여주고 보안 담당자의 승인 아래 관련 위치를 재평가한다. 이미 개설된 건은 시험 건을 운영 건으로 이름만 바꾸지 않는다. 이전 건의 이력과 링크를 보존하고 올바른 구분에서 새 건 또는 기존 건 연결 여부를 결정한다. 교정 중인 항목은 운영 집계에서 검증된 값인 것처럼 세지 않는다. 합성 시험 범위를 `PRODUCTION`으로 바꾸는 교정은 거부한다.

**현행:** V8의 GitHub 수동 분류는 `UNCLASSIFIED`에서 한 번 `TEST` 또는 `PRODUCTION`으로만 바뀌며 교정 API와 혼합 범위 분리는 없다. 새 승인 흐름과 교정이 구현되기 전까지 화면에서 이 목표를 수행 가능한 동작으로 표시하지 않는다.

## 2. 근거를 먼저 보여주는 판정

탐지 목록은 고유 키 인벤토리다. 보안 담당자의 작업 대기열은 그중 **결정할 항목**만 골라낸다. 위치마다 아래 사실을 구분해 보여주고, 판단에 쓰인 관측 시각·실행 ID·룰 또는 정책 버전과 원천을 연결한다.

| 확인할 사실 | 화면과 판정의 기준 |
|---|---|
| 탐지 | 발급자·유형·구성요소, 마스킹 식별자, Finding 룰과 시각. 형식 일치만으로 실제 키나 노출을 확정하지 않음 |
| 위치와 보관 정책 | 권한에 맞게 제한된 원천·객체·경로, 승인 수집 범위, 별도 보관 허용 정책 및 그 버전. 수집 승인과 보관 허용을 혼동하지 않음 |
| 최신성·범위 | 마지막 완전 수집, 마지막 발견, 이후 부분 실패·미수집, 검사한 브랜치·파일 또는 객체 범위. 읽지 못한 범위를 `0건`으로 표시하지 않음 |
| 유효성·영향 | 유형별 검증 결과와 이유·시각, 확인된 주체·권한·대상 및 미확인 항목. 인증 성공만으로 악용이나 실제 사용을 주장하지 않음 |
| 이전 판단 | 같은 위치의 마지막 판정, 판정 때 사용한 근거와 현재 사실의 차이, 연결된 대응 건과 남은 조치 |

노출 판정은 다음처럼 **서로 다른 사실**로 기록한다.

| 결과 | 의미와 후속 동작 |
|---|---|
| `ABNORMAL` | 실제 자격 증명이 승인되지 않은 보관·공개 위치에 있다고 근거로 확인. 지원되는 범위에서 한 번의 `노출 확인 및 조치 요청`으로 새 건을 열거나 같은 키·구분의 현재 건에 이 위치를 연결 |
| `NORMAL` | 실제 자격 증명이 버전과 기간이 유효한 보관 허용 정책에 맞게 있는 위치. 정책 근거와 확인 시각을 저장하며 대응 건을 만들지 않음 |
| `FALSE_POSITIVE` | 후보 문자열이 자격 증명이 아님이 확인된 탐지 오류. 탐지 Finding은 이력으로 보존하고 정상 보관 위치나 위험 수용으로 세지 않음 |
| `UNKNOWN` | 원천 맥락, 보관 정책, 구성요소, 키 실재 여부 등의 근거가 부족하거나 상충. 추정으로 `NORMAL`·`ABNORMAL`·`LOW`·`PROD`에 넣지 않고 보안 검토 대기열에 남김 |

`FALSE_POSITIVE`는 키 후보·발견 결과의 교정이고 `NORMAL`은 실제 키의 허용된 보관이다. `INVALID`, `UNCHECKED`, `UNKNOWN` 유효성은 노출 결과와 독립이다. 만료·폐기가 신뢰할 수 있는 근거로 확인된 신규 발견은 위치와 검증 이력을 보존하되 활성 사고를 자동 생성하지 않는다. 원인을 모르는 인증 거절은 폐기 근거가 아니다. AWS 또는 K8s의 정상 비밀 저장소 값이나 IAM `METADATA_ONLY` 목록 관측은 그것만으로 비정상 노출이 아니다.

판정은 위치별로 수행자, 사유 코드, 근거 ID와 관측 시각, 정책·범위·Finding 버전, 변경 전후, 시각을 추가 전용으로 저장한다. 판단 규칙은 먼저 권고와 부족 근거를 만들 수 있으나 **형식 탐지 단독으로 운영 노출을 확정하거나 대응 건을 열지 않는다**. 오탐·정상 판정도 정책 증거 없이 자동 확정하지 않는다. 새로운 원천 버전, 보관 정책 변경, 분류 교정, 추가 노출 증거 또는 판정 후의 불완전 수집은 판정 이력을 삭제하지 않되 현재 판단의 최신성 또는 적용 가능성을 다시 확인할 대상으로 표시한다. 재스캔으로 수동 판정을 무조건 덮지 않는다.

부족한 근거는 `UNKNOWN`으로 끝내지 않는다. 확인해야 할 구체적 질문, 이유 코드, 책임 팀·사람, 기한과 비밀을 제거한 티켓·변경 참조를 가진 **확인 작업**으로 남긴다. 기한이 지나거나 새로운 근거가 도착하면 재검토 대기열에 다시 올린다. 소유자를 아직 모르면 보안 담당자를 임시 확인 담당자로 지정하고 소유자 확인을 별도 질문으로 둔다. 미확인 상태를 완료·예외·정상으로 집계하지 않는다. 키 원문, 공급자 오류 본문과 자유 메모는 근거 참조에 넣지 않는다.

**현행:** V8은 활성 GitHub 범위의 `CONFIRMED`·`PRESENT` 위치에 Finding ID를 골라 `ABNORMAL` 또는 `NORMAL`을 수동 저장한다. 보관 허용 정책과 `FALSE_POSITIVE` 교정, 근거 기반 작업 대기열, 담당자·기한을 가진 판정 전 확인 작업은 아직 없다. V12의 `NEEDS_MORE_INFO`는 이미 열린 건의 검토 이력과 안전한 참조만 저장한다.

## 3. 노출 확인과 대응 건 개설

보안 담당자의 목표 화면에서 `노출 확인 및 조치 요청`은 **하나의 원자 명령**이다. 서버는 해당 연결의 `SECURITY` 권한과 승인 범위, `TEST`·`PRODUCTION` 구분, 같은 위치의 최신 근거, `CONFIRMED` 자격 증명, `PRESENT` 상태 및 위치·범위·보관 정책 버전을 다시 확인한다. 요청은 노출 사유와 선택한 근거를 받아 위치의 `ABNORMAL` 판정 이력을 저장하고, 같은 트랜잭션에서 같은 키·구분의 현재 대응 건을 찾는다. 없으면 `OPEN` 건을 하나 만들고 위치를 연결한다. 있으면 새 건을 만들지 않고 그 위치만 연결한다. 성공 응답은 생성·연결 구분과 건 ID, 연결 위치 ID, 현재 버전, 다음 행동을 반환한다. 멱등 키와 고유 제약으로 재시도·동시 요청의 중복 건과 중복 위치를 막는다.

새 건에 연결할 때 이미 확인된 같은 키·같은 구분의 다른 `ABNORMAL` 위치도 권한과 최신 버전을 확인해 연결하거나, 권한이 달라 보이지 않는 위치는 보안 조정자에게 별도 연결 대기 작업으로 남긴다. 현재 건에 새 위치가 붙으면 위치별 미완료 조치로 표시하고 완료·해결 조건을 다시 계산한다. `UNKNOWN` 위치를 자동으로 비정상으로 바꾸거나 같은 키라는 이유로 정상 위치까지 붙이지 않는다. 호출자에게 권한 밖 위치의 이름·수·세부 근거를 유출하지 않고, 권한 있는 조정자에게만 제한된 범위 누락을 표시한다. 이미 해결한 건에는 새 위치를 붙이지 않으며 새로운 노출이면 이전 건과 연결된 새 건을 만든다.

새 비정상 위치가 `REVALIDATION_PENDING` 건에 연결되면 그 위치의 조치는 아직 시작되지 않았으므로 건을 같은 트랜잭션에서 `IN_PROGRESS`로 되돌리고 새 위치의 조치 주기를 연다. `OPEN` 건은 `OPEN`, 이미 `IN_PROGRESS`인 건은 그 상태를 유지한다. 단계·버전·전이 사유와 이전 재검증 근거를 이력에 남기고 재검증 대기 건수와 해결 가능 여부를 다시 계산한다. 기존 위치의 성공 근거는 삭제하지 않되 새 위치를 해결 조건에서 빼지 않는다.

이 원자 명령 자체가 보안 담당자의 **확정 판정**이다. 같은 근거를 대응 건에서 다시 `CONFIRMED` 검토하는 단계는 목표 흐름에서 요구하지 않는다. 필요하면 별도 보안 재검토는 새로운 증거나 판정 교정의 목적을 명시해 이력으로 남긴다. 판정 후 건 개설을 취소하거나 되돌리는 버튼은 제공하지 않는다. 잘못 확인한 노출은 오탐·범위 제외·정상 보관 교정 절차로 처리하고 과거 감사 기록과 이미 수행된 조치를 숨기지 않는다.

**현행:** V8은 `POST /occurrences/{occurrenceId}/assessments`로 판정을 먼저 저장하고 `POST /secrets/{secretId}/cases`로 **선택한 위치 한 곳만** 개설한다. 같은 키·구분의 현재 건이 있으면 409와 기존 건 안내를 주지만 새 위치를 추가할 수 없다. V9–V12는 열린 건에서 별도의 `CONFIRMED` 검토를 요구한다. 새 원자 명령을 도입해도 **고정된 전환 시각 이전에만** 기존 변경 API와 응답을 유지하며 새 화면은 새 명령을 사용한다. 전환 이후 구 판정·개설·해결 쓰기는 차단하고, 구 건의 검토·조치만 권한 검사를 거쳐 이어갈 수 있다. 새 방식으로 연 건에는 해당 보안 결정을 검토 충족 근거로 연결하고 별도의 반복 클릭을 요구하지 않는다. 기존 `UNREVIEWED` 건을 마이그레이션만으로 일괄 `REVIEWED`로 바꾸지 않는다. 이전 확정·추가 확인·판정 이력은 그대로 읽을 수 있게 두고, 이전 미검토 건은 기존 검토를 마치거나 새 보안 결정으로 전환한 뒤 진행한다.

## 4. 독립 상태와 담당자

| 축 | 값 | 변경 근거 |
|---|---|---|
| 유효성 | VALID, INVALID, UNKNOWN, UNCHECKED | 유형별 검증 시도와 공급자 근거 |
| 위치별 노출 | ABNORMAL, NORMAL, UNKNOWN | 위치에 적용되는 보관 정책 및 원천 근거와 보안 결정 |
| 탐지 교정 | FALSE_POSITIVE 또는 교정 없음 | 실제 자격 증명이 아닌 후보·Finding에 대한 별도 판정. NORMAL이나 INVALID로 저장하지 않음 |
| 심각도 | CRITICAL, HIGH, MEDIUM, LOW, 미평가 | 확인된 노출·권한·대상과 버전이 있는 평가 규칙 |
| 조치 | OPEN, IN_PROGRESS, REVALIDATION_PENDING, RESOLVED | 대상 위치별 조치·재검증 및 보안 해결 결정 |
| 예외 | 없음, RISK_ACCEPTED | 별도 승인자·범위·사유·만료와 재검토 |
| 최신성 | 최근 시도, 마지막 성공, 다음 예정, 지연, 조치 이후 미검증 | 실행과 증거의 관측 시각·검사 범위 |

판정 대기, 확정 노출, 담당자 미지정, 외부 조치 대기, 재검증 실패는 서로 다른 **업무 대기열**로 보여준다. 검토 완료나 체크리스트 완료를 유효성, 심각도 또는 해결 상태로 바꾸지 않는다. 기존 `reviewStatus`와 `NEEDS_MORE_INFO` 이력은 전환 중 읽기·필터 호환을 위해 보존하되 새 흐름의 진실 원천은 노출 결정, 확인 작업 및 위치별 조치 근거다. `NEEDS_MORE_INFO`를 다시 쓰는 경우 실제 부족 사실, 확인 책임자, 기한과 제한된 근거 참조가 있어야 한다. 정보 부족은 조치가 필요한 것으로 이미 확정된 다른 위치의 긴급 대응을 멈추는 일괄 잠금이 아니다.

대응 건에는 전체 조정을 책임지는 보안 담당자를 두고, 연결된 위치마다 범위 권한을 갖춘 개발·인프라 조치 담당자를 지정할 수 있어야 한다. 서로 다른 저장소·문서·클라우드 위치의 담당자가 달라도 한 키의 대응 건과 위치별 진척을 유지한다. 담당자는 자신에게 허용된 위치의 안전한 원천 식별과 해야 할 조치를 볼 수 있어야 한다. 권한이 없는 위치는 세부 내용을 가리고 보안 조정자에게 연결·배정 문제를 알린다. 팀 또는 사람의 지정·변경은 수행자, 사유, 시각과 버전을 남기며 지정만으로 외부 조치나 해결을 주장하지 않는다.

**현행:** V7–V12에는 대응 건 단위의 팀·개인 담당자와 연결 범위별 `SECURITY`·`REMEDIATOR` 역할이 있다. 조치 담당자의 모든 연결 권한을 요구하며 위치별 별도 담당자와 조정자, 권한에 맞는 충분한 원천 근거 화면은 아직 목표다.

## 5. 외부 조치, 재검증과 해결

제품은 외부 공급자의 키를 직접 교체·폐기·재발급하거나 권한을 변경하지 않는다. 담당자가 실제로 수행한 `ROTATED`, `REVOKED`, `REMOVED_FROM_SOURCE`, `PERMISSION_REDUCED`를 위치와 수행 시각, 수행자, 비밀을 제거한 증거 참조와 함께 추가 전용으로 기록한다. **기록은 자기 신고이며 공급자 상태의 자동 검증 결과가 아니다.** 같은 위치에 여러 조치를 남길 수 있다. 체크리스트와 AI 가이드는 일을 돕는 안내이며 완료 여부가 재검증이나 해결의 독립적인 게이트가 아니다. `PERMISSION_REDUCED`만으로 노출 제거 또는 자격 증명 무효화를 주장하지 않는다.

| 현재 | 의미 있는 요청과 조건 | 다음 |
|---|---|---|
| OPEN | 위치별 담당자가 첫 실질 외부 조치를 증거와 함께 기록 | IN_PROGRESS |
| IN_PROGRESS | 위치별 실질 조치가 기록되고 담당자가 해당 위치를 재확인 대상으로 제출. 아직 끝나지 않은 위치가 있으면 건은 계속 조치 중 | 해당 위치만 REVALIDATION_PENDING; 모두 제출됐을 때 건도 REVALIDATION_PENDING |
| REVALIDATION_PENDING | 같은 승인 범위에서 **조치 이후** 수집·탐지가 완전히 성공했고 탐지 설정·식별 기준이 비교 가능 | 위치별 PRESENT, MISSING 또는 UNKNOWN 결과를 기록 |
| REVALIDATION_PENDING | PRESENT를 확인한 담당자가 재조치를 명시적으로 시작 | 해당 위치 IN_PROGRESS, 이력 보존 |
| 미해결 상태 | 승인권자가 유효 기간·위치 범위·사유를 가진 위험 수용을 승인 | 해결과 구분한 RISK_ACCEPTED 예외 |
| RESOLVED 이후 | 동일 키·구분의 새로운 비정상 노출을 확인 | 이전 건을 보존하고 새 OPEN 건 |

수집 실패, 부분 실패, 범위·브랜치 불일치, 원문 재취득 실패, 비교 설정 변경은 `MISSING`의 증거가 아니다. 마지막 성공 결과와 최근 실패 시도는 함께 보이되 실패로 성공 시각을 갱신하지 않는다. `MISSING`은 **검사한 현재 원천 범위에서 해당 키를 다시 찾지 못했다**는 뜻이지 키 폐기, Git 이력 전체 제거, 다른 원천 안전성 또는 악용 부재를 뜻하지 않는다. 새 위치를 발견했거나 같은 키의 `UNKNOWN` 현재 위치가 있으면 조정자가 판단할 때까지 전체 해결을 보류한다. 검사에서 `PRESENT`가 다시 나오면 지난 조치 기록을 지우지 않고 새 조치 주기를 만든다.

보안 담당자의 `해결` 요청은 다음을 모두 확인한 뒤에만 허용한다.

1. 현재 건의 모든 `ABNORMAL` 위치가 연결돼 있고 각 위치의 마지막 실질 조치 **이후** 완전하고 비교 가능한 검사에서 `MISSING`임이 확인됐다. 연결되지 않은 새 비정상 위치가 없어야 하며, 같은 키의 현재 `UNKNOWN` 위치는 근거를 갖춰 `ABNORMAL`, `NORMAL` 또는 Finding 오탐으로 판정해야 한다. 현재 위치가 실제 키 후보인데 조사 불가·범위 밖이라는 이유만으로 `RESOLVED`에서 제외할 수 없다. 남은 위험은 기한·범위를 정한 위험 수용에서 관리한다.
2. 외부에서 자격 증명을 폐기·교체했다는 근거를 별도로 확인한다. 공급자 검증이나 안전한 폐기·교체 이력이 있으면 방법·시각·범위를 기록한다. 조치 기록만 있거나 사유 불명 `INVALID`만으로 완료 처리하지 않는다. 자동 검증이 불가능하면 승인된 담당자의 제한된 증빙과 보안 담당자의 명시적 수동 확인을 기록하며 무엇을 확인하지 못했는지 남긴다. 폐기·교체 여부를 어떤 방법으로도 확인할 수 없다면 `REVALIDATION_PENDING` 또는 별도 위험 수용에 남긴다.
3. 검사하지 않은 Git 이력, 다른 브랜치·원천, 공급자 사용·악용 이력 등의 한계를 해결 화면과 이력에 적는다. 지원 범위의 노출 제거와 자격 증명 조치가 확인됐어도 이 영역까지 안전하다고 선언하지 않는다. 해결 상태에는 `FULL` 또는 `LIMITED` 확인 범위와 남은 미확인 사항을 붙여 표현한다. `FULL`은 선언된 지원·승인 범위의 필수 확인이 전부 성공했고 확인 대기 사실이 없는 경우에만 사용하며, 전 세계의 모든 복사본이 없다는 뜻이 아니다. 지원되지 않는 이력·원천이나 수동으로만 확인한 사실이 남으면 `LIMITED`를 표시한다. `LIMITED`는 이미 확인된 미해결 위치나 실패한 필수 재검증을 무시하는 우회 수단이 아니다.
4. 보안 담당자가 근거 ID, 범위·정책 버전, 확인 시각과 승인자를 고정해 요청한다. 서버가 최신 상태와 버전을 다시 검사하고 감사 이벤트를 남긴다.

정상 보관 위치나 만료·폐기 이력만 있으면 신규 대응 건 없이 인벤토리·이력에 둔다. 이미 열린 건은 한 위치의 미발견, 외부 조치 기록, 유효성 변경, 체크리스트 완료만으로 자동 해결하지 않는다. **모든** 연결 위치의 원래 노출 판정이 오류였음이 새 근거로 증명되면 `SECURITY`가 `FALSE_POSITIVE` 또는 `OUT_OF_SCOPE` 교정 종료를 별도로 승인한다. 건의 `disposition`과 `closed_at`을 기록하고 `is_current=false`로 만들되 `RESOLVED`·`RISK_ACCEPTED`·운영 해결 건수에 넣지 않는다. 한 위치라도 실제 미해결 노출이면 건 전체를 교정 종료하지 못한다. 과거 조치·판정 이력은 보존한다. 위험 수용은 위험이 남아 있는 기간 한정 결정이다. 만료·취소·승인 범위 밖 새 노출이 있으면 미해결 단계로 되돌리고 지난 승인은 보존한다.

`TEST`는 출처 구분이지 발견한 자격 증명이 가짜라는 보장이 아니다. 합성 fixture 목록·버전과 해당 키의 일치가 확인된 시험 건만 `FIXTURE_RETIRED` 증거, 조치 이후 비교 가능한 재검사와 `SIMULATION` 확인 범위로 **시험 시나리오 종료**할 수 있다. 공급자 자격 증명의 폐기를 검증했다고 표시하지 않는다. **완전한 값 후보가 최신 성공 검사에서 현재 발견됐고 유효 Finding이 남은 경우**에만 키별 합성 증명이 없는 `POSSIBLE_REAL`은 시험 종료를 막고 **즉시** 운영 보안 담당자의 실키 의심 경고와 담당자·기한으로 보여준다. 불완전 후보·메타데이터만 관측한 항목·모든 Finding이 오탐인 위치는 이 경고에 넣지 않고 별도 조사·인벤토리에서 다룬다. 아직 대응 건을 열 수 없는 후보라면 경고를 조사 과제에 연결하고, 시험 대응 건이 있으면 그 건에 연결한다. 같은 키의 반복 검사는 열린 경고를 갱신한다. 공급자 근거로 실제 키가 확인되면 경고를 실키 확인으로 승격하고 폐기·교체 근거가 갖춰질 때까지 건을 미해결로 둔다. 나중에 키별 fixture 일치 또는 모든 관련 Finding의 오탐이 증명되면 반증을 검토해 경고를 닫을 수 있다. 인지 기록만으로 닫지 않는다. 시험 출처 기록은 유지하며 운영 조치 대시보드에는 이 경고를 **별도 단위**로 표시해 시험 건을 운영 대응 건으로 중복 집계하지 않는다.

**현행:** V10은 승인 GitHub **현재 파일** 한 위치의 비교 가능한 `MISSING`을 확인하고 연결된 모든 위치가 해당 조건을 만족하면 보안 담당자의 `RESOLVED` 요청을 허용한다. Git 이력·다른 원천·공급자 폐기 증빙을 해결 게이트로 검사하지 않는다. V11–V12 로컬 UX 변경은 조치 기록과 위치별 `기록 마침`을 분리했으며 백엔드·프런트엔드가 배포돼 있음을 이 문서만으로 보장하지 않는다. 위의 생애주기 증빙, 확인 범위 `FULL`·`LIMITED`, 위치별 담당과 교정·예외는 목표다.

## 6. 집계와 화면 약속

기본 운영 화면의 네 조치 단계는 `PRODUCTION`의 각 키별 현재 ResponseCase만 센다. 별도 전체 위험 수용 예외와 네 단계는 서로 배타적이며 **네 단계 합계 + 전체 예외 수 = 같은 필터의 현재 대응 건 목록 수**다. 일부 위치만 위험 수용하고 다른 미해결 위치가 있으면 건은 조치 단계에 센다. `TEST`는 명시적 시험 화면에서만 같은 규칙으로 세고 운영 현황·통합 현황·CSV의 운영 사고 수에 더하지 않는다. 탐지 후보, 정상 인벤토리, `METADATA_ONLY`, 판정 대기·오탐·만료 이력은 각각 별도 숫자와 대기열로 표시한다. 스캔 실행 수, 고유 키 수, 위치 수와 대응 건 수를 혼용하지 않는다.

요약 카드·매트릭스·대응 목록은 같은 구분, 필터, 집계 단위와 기준시점으로 계산한다. 발견 소스·환경 필터가 한 건의 여러 위치에 걸려도 대응 건은 한 번만 센다. 화면에는 확인된 사실, 미확인 이유, 현재 소유자와 **지금 해야 할 한 가지 행동**을 먼저 보여주고 자세한 감사 이력은 별도로 열어본다. 결과가 없을 때는 실제 0건, 권한 없음, 연결 미설정, 부분 검사, 데이터 미제공을 구분한다.

## 7. 전환과 수용 사례

새 경로가 배포되고 과거 건·권한·근거를 확인한 뒤 전환 시각을 고정한다. 이후 구 V8 범위 분류·위치 판정·건 개설과 구 `/resolve`의 **쓰기**는 중단하고 이력 조회만 유지한다. 전환 전 개설한 건도 해결은 새 근거 계약으로만 결정한다. 건별 `LEGACY|EVIDENCE_V1` 버전과 전환 시각을 남겨 옛 경로로 새 건을 만들거나 약한 재검사 근거만으로 닫는 우회를 막는다.

기존 V7–V12 테이블과 이력은 삭제하거나 과거 상태를 추정해 다시 쓰지 않는다. 새 확인 작업, 보관 정책 근거, 위치별 소유·조치, 사례 연결과 해결 증빙은 새 버전 마이그레이션으로 **추가**한다. 구 V8 판정·건 개설과 구 해결 API는 **전환 시각 전까지만** 기존 호출자를 위해 유지하고 그 뒤 `410 LEGACY_WRITE_DISABLED`로 막는다. V9–V12의 구 건 검토·조치 API는 해당 `LEGACY` 건에 한해 권한·버전을 다시 검사하며 유지하고, 새 건에는 새 원자 명령과 위치별 조치 계약을 적용한다. 기존 응답의 enum을 예고 없이 바꾸지 않는다. 이전 한 위치짜리 건은 같은 키·구분의 다른 위치를 권한과 판정 근거로 재조사해 연결하며, 확정되지 않은 위치는 연결 대기와 해결 차단 사유로 보여준다. 기존 `RESOLVED` 건은 당시 확인 범위만 기록된 **이전 방식 해결**로 표시하고 현재 기준의 공급자 폐기·다른 원천 확인을 완료했다고 소급 주장하지 않는다. 이전 `NEEDS_MORE_INFO` 이력은 보존하고 담당자·기한이 없는 과거 기록은 새 확인 작업으로 전환할 때 보완한다.

아래 사례를 화면·API·마이그레이션 시험의 완료 조건으로 삼는다.

- 동일 키가 GitHub 파일 두 곳에 있고 둘 다 `ABNORMAL`이면 한 운영 대응 건에 두 위치가 연결된다. 한 곳만 지워졌거나 한 곳의 검사가 부분 실패하면 전체 해결은 거부되고 막힌 이유가 보인다.
- 같은 키가 승인된 Secret 저장소와 GitHub 평문 파일에 있으면 저장소는 `NORMAL` 인벤토리, GitHub는 `ABNORMAL` 대응 위치다. 수집 승인만으로 GitHub 위치가 `NORMAL`이 되지 않는다.
- 완전하지 않은 후보와 형식 오탐은 각각 `UNKNOWN` 확인 작업과 `FALSE_POSITIVE` 이력으로 남고, 둘 다 운영 사고 건수에 들어가지 않는다.
- 검증이 `UNKNOWN`이어도 노출이 근거로 확인되면 조치 요청은 가능하다. 검증 오류를 무효나 낮은 심각도로 바꾸지 않는다.
- 새 운영 위치, 범위 교정 또는 새로운 정책 근거가 오면 기존 수동 판정 이력은 유지하되 현재 판단의 유효성과 해결 가능성을 다시 계산한다.
- 외부에서 키를 제거했다고 기록한 뒤 실행이 실패하거나 `PRESENT`이면 해결하지 않는다. 현재 파일 `MISSING`만으로 공급자 폐기를 주장하지 않는다.
- 구 URL과 API는 전환 중 기존 상태를 읽을 수 있고, 권한 밖 위치와 키 원문은 응답·오류·감사에 나타나지 않는다. 버전 충돌·중복 요청은 이중 개설 또는 이중 조치를 만들지 않는다.
