# 대응 단위와 상태 전이

기준: [PRD](../01-requirements/PRD.md), [ADR-S002](../03-architecture/adr/ADR-S002.md), [ADR-S003](../03-architecture/adr/ADR-S003.md), [ADR-S004](../03-architecture/adr/ADR-S004.md)

## 1. 처리 단위

CredentialSet은 동일한 인증 수단의 구성요소를 묶는다. 동일성을 증명할 수 없는 불완전 후보는 다른 후보와 임의로 합치지 않는다. Occurrence는 수집원, 원본 위치와 버전이 지정된 발견 위치다. 서로 다른 엔진이 같은 원본 위치와 같은 키를 찾으면 탐지 근거는 각각 남기되 Occurrence는 하나로 센다.

ResponseCase는 한 CredentialSet의 비정상 노출에 대한 대응 기록이다. 운영 범위에서는 한 CredentialSet에 한 시점의 현재 대응 건을 최대 하나 둔다. 합성 시험용 `TEST`는 별도 시뮬레이션 범위이므로 동일 키에 시험·운영 건이 각각 하나씩 존재할 수 있다. 시험 건과 위치는 운영 건에 합치거나 운영 사고 수에 포함하지 않는다. 여러 노출 위치는 같은 범위의 건에 연결하고 위치마다 노출 판정, 조치, 재확인 근거를 따로 보존한다. 해결 후 같은 범위에서 새로운 노출이 발생하면 새 대응 건을 열고 이전 건은 이력으로 보존한다. 기존 노출의 재발견은 해당 범위의 현재 건 위치 이력으로 갱신한다.

### 수동 노출 판정과 대응 건 개설

수집한 범위의 대응 구분은 처음에 `UNCLASSIFIED`다. 해당 연결의 `SECURITY` 권한을 가진 담당자가 승인된 시험 원천이면 `TEST`, 운영 원천이면 `PRODUCTION`으로 명시적으로 분류하고 허용된 사유 코드, 수행자, 시각과 범위 버전을 추가 전용 이력에 남긴다. 저장소가 GitHub에 있거나 키 유형이 AWS라는 이유만으로 운영으로 분류하지 않는다. 합성 표본 저장소는 시험 범위로만 분류하며 시험 건을 운영 건수에 합치지 않는다.

이 대응 구분은 발견 위치의 `PROD`·`DEV`·`UNKNOWN` 환경 분류와 다른 축이다. 시험 원천의 환경이 `UNKNOWN`이어도 `TEST` 대응 건으로 다룰 수 있지만 환경을 임의로 `PROD`로 채우지 않는다. 현재 수동 분류·판정 기능은 활성 GitHub 연결에 한정하며, 한 번 분류한 범위의 재분류와 오분류 교정 절차는 후속 운영 설계가 필요하다.

형식 탐지 `Finding`은 특정 위치에 키 후보가 있다는 근거다. 비정상 노출의 자동 증명이나 유효성 검증 결과는 아니다. 보안 담당자는 원문을 제외한 위치와 Finding ID·룰·탐지 시각을 확인하고 해당 위치에 속하는 Finding ID를 지정해 `ABNORMAL` 또는 `NORMAL`을 수동 판정한다. 판정 사유는 허용된 코드로만 기록하며 수행자, 시각, 변경 전후 상태와 버전을 이력으로 보존한다. 근거가 부족하면 `UNKNOWN`을 유지하고 대응 건을 열지 않는다. 검증 결과 `UNCHECKED` 또는 `UNKNOWN`을 노출 판정으로 치환하지 않는다. 원문 키와 임의 문장은 입력·응답·감사 기록에 넣지 않는다.

대응 건은 분류된 활성 범위의 현재 `ABNORMAL`·`PRESENT` 위치와 최신 수동 판정, 일치하는 버전을 서버가 다시 확인한 뒤 보안 담당자의 별도 요청으로 연다. 판정 저장만으로 자동 개설하지 않는다. 다시 스캔해도 수동 노출 판정은 임의로 `UNKNOWN`으로 덮어쓰지 않는다. 이번 기본 흐름에서 이미 개설한 건의 근거 위치를 `NORMAL`로 바꾸는 동작은 오탐·대상 제외 절차가 마련될 때까지 허용하지 않는다.

현재 개설 API는 선택한 한 위치만 새 건에 연결한다. 같은 키와 대응 구분에 이미 현재 건이 있으면 그 건의 ID를 조회해 보여주되 새 건은 열지 않는다. 다른 위치를 그 건에 추가 연결하는 절차는 후속 구현이다. 위의 여러 위치 단위 대응 정책은 그 연결 절차까지 완료했을 때의 목표 계약이다.

정상 비밀 저장소의 값 존재, 불완전 후보, 검증 미지원 또는 검증 불가는 그 사실만으로 사고가 아니다. 비정상 노출 근거가 확인되면 유효성 UNKNOWN 또는 UNCHECKED라도 대응 건을 만들고 수동 검토에 올린다. 신규 발견 시 만료 또는 폐기가 확인되면 대응 건을 만들지 않고 발견, 검증 이력을 보존한다. 사유를 알 수 없는 INVALID는 만료 또는 폐기로 추정하지 않고 검토 대상으로 둔다.

## 2. 독립 상태

| 축 | 값 | 변경 근거 |
|---|---|---|
| 유효성 | VALID, INVALID, UNKNOWN, UNCHECKED | 유형별 검증 시도와 공급자 근거 |
| 심각도 | CRITICAL, HIGH, MEDIUM, LOW, 미평가 | 확인한 노출, 주체, 권한, 자원, 환경과 정책 버전 |
| 검토 | UNREVIEWED, REVIEWED | 권한 있는 담당자의 검토 기록 |
| 조치 | OPEN, IN_PROGRESS, REVALIDATION_PENDING, RESOLVED | 대응 건의 위치별 조치 및 재확인 증거 |
| 예외 | 없음, RISK_ACCEPTED | 승인자, 사유, 범위, 만료 시각이 있는 위험 수용 |
| 최신성 | 최근 시도, 마지막 성공, 다음 예정, 지연, 조치 이후 미검증 | 스케줄과 시점별 실행 이력 |

`CONFIRMED` 검토만 `REVIEWED`로 기록한다. `NEEDS_MORE_INFO`는 `SOURCE_CONTEXT_MISSING`(원천 맥락 부족), `OWNER_UNCONFIRMED`(소유자 미확인), `EXPOSURE_EVIDENCE_MISSING`(노출 근거 부족) 중 하나와 제한된 티켓·변경 참조를 필수로 남긴다. 그 검토를 수행한 보안 담당자가 후속 확인 담당자다. `NEEDS_MORE_INFO`는 이력에 남기되 `UNREVIEWED`와 `OPEN`을 유지하며 대응 시작·외부 조치 권한을 열지 않는다. 이전 고정 사유 `INSUFFICIENT_EVIDENCE` 기록은 이력에서 유지하지만 새 검토 요청에는 허용하지 않는다. 검토 완료, 체크리스트 완료, 담당자 지정은 유효성이나 조치 상태를 자동으로 바꾸지 않는다. 체크리스트는 업무 보조 기록이고 4/4 완료를 재검증 요청이나 해결의 필수 조건으로 사용하지 않는다. 검증 불가도 위험 수용 예외가 아니다.

## 3. 조치 전이

| 현재 | 요청 또는 근거 | 다음 | 허용 조건 |
|---|---|---|---|
| OPEN | 담당자가 대응 시작 | IN_PROGRESS | 확정 검토 뒤 지정된 `REMEDIATOR`와 사유·버전 기록 |
| OPEN | 외부 조치 기록 요청 | 전이 없음, 요청 거부 | 검토·담당자 지정만으로 조치 기록을 열지 않음. `start`로 건을 먼저 `IN_PROGRESS`에 전이해야 함 |
| IN_PROGRESS | 외부 조치 기록 | IN_PROGRESS 유지 | 지정된 `REMEDIATOR`가 위치·종류·실제 시각·제한된 증거 참조를 추가 전용으로 기록. 같은 위치에 여러 조치 허용. 제품은 외부 키를 변경하지 않음 |
| IN_PROGRESS | 위치별 기록 마침 | 해당 위치는 REVALIDATION_PENDING; 모든 연결 위치가 대기면 건도 REVALIDATION_PENDING | 해당 위치의 이번 조치 주기에 `ROTATED`, `REVOKED`, `REMOVED_FROM_SOURCE` 중 하나 이상이 있어야 함. `PERMISSION_REDUCED`만 있으면 거부. 다른 미완료 위치가 있으면 건은 IN_PROGRESS 유지 |
| REVALIDATION_PENDING | 재검증에서 `PRESENT` 확인 후 명시적 재조치 요청 | IN_PROGRESS | 해당 위치의 결과와 변경 이력을 연결. `UNKNOWN`은 해결 근거가 아니며 자동 재조치도 아님 |
| REVALIDATION_PENDING | 해결 검토 | RESOLVED | 보안 담당자가 모든 연결 위치의 최신 조치 이후 비교 가능한 `MISSING`과 동일한 현재 범위 버전을 확인. 위험 수용만으로 해결 처리하지 않음 |
| 모든 미해결 단계 | 위험 수용 승인 | RISK_ACCEPTED 별도 예외 | 승인 권한, 위치 범위, 사유, 만료 시각 기록. 남은 미해결 노출이 모두 승인 범위에 있을 때만 대응 건 전체를 예외로 분류 |
| RISK_ACCEPTED | 만료, 취소, 범위 밖 새 노출 | OPEN 또는 IN_PROGRESS | 남은 위험에 따라 재개하고 이력 보존 |
| RESOLVED | 새 노출 발견 | 새 대응 건의 OPEN | 이전 건과 연결하고 이전 해결 기록 보존 |

검증 실패나 원문 재취득 실패는 해결 증거가 아니다. 외부 키의 폐기가 확인돼도 과거 악용과 다른 노출 위치를 검토하기 전에는 기존 대응 건을 자동 해결하지 않는다. 모든 상태 변경은 버전 확인과 감사 이력을 동반한다.

`PERMISSION_REDUCED`는 접근 위험을 줄이기 위해 외부에서 수행한 조치의 기록이다. 현재 재검증의 해결 근거는 승인된 GitHub 현재 파일에서 비교 가능한 키 미발견이므로 권한 축소만으로는 위치별 기록 마침이나 해결을 허용하지 않는다. 재검증에서 `PRESENT`가 나오면 명시적으로 재조치를 시작하고 이전 주기의 기록은 보존한다. 새 주기를 마치려면 그 이후의 실질 조치 기록을 다시 확인한다. 재검증 `UNKNOWN`, 실행 실패나 부분 실패는 `MISSING`으로 간주하지 않는다.

## 4. 집계 계약

기본 화면 범위는 `PRODUCTION`의 현재 대응 건이다. 각 CredentialSet의 최신 운영 건을 한 건만 선택하므로 이 범위에서 대응 건 수와 고유 키 수가 같다. `TEST` 건은 명시적인 시험 조회에서만 세며 운영의 네 단계·예외·심각도·통합 현황 수에 합치지 않는다. 같은 키가 두 범위에 있어도 각 범위 안에서는 한 번만 센다. 정상 인벤토리와 대응 건이 없는 만료, 폐기 이력은 별도 범위에 표시한다. 과거 대응 건은 이력 화면에서 조회하며 현재 수에 합치지 않는다.

같은 필터와 기준시점에서 네 조치 단계 수의 합과 별도 예외 수는 현재 대응 건 목록 수와 같다. 남은 미해결 노출 위치가 모두 승인된 위험 수용 범위에 있을 때만 예외에 한 번 센다. 일부 위치만 승인됐고 다른 미해결 노출이 있으면 조치 단계에 센다. 심각도, 유효성 매트릭스와 미지정 목록도 같은 현재 대응 건을 기본 모수로 사용하며 클릭 후 목록에 동일한 필터, 기준시점, 집계 단위를 전달한다. 발견 위치 수와 엔진 탐지 수는 별도 지표다.

환경을 알 수 없는 SaaS 위치는 UNKNOWN으로 표시한다. 필터는 발견 소스, 발급자, 환경, 키 유형, 유효성, 심각도, 조치 단계, 예외와 담당자를 구분한다. 필터 범위와 기준시점은 API 응답과 화면에 함께 표시한다.

발견 소스 또는 환경 필터는 해당 조건의 발견 위치가 하나라도 있는 대응 건을 한 번 선택한다. 선택된 건의 조치 단계와 대표 심각도는 전체 비정상 노출 위치의 현재 상태다. 같은 건이 서로 다른 소스별 화면에 각각 나타날 수 있지만 `ALL` 집계에는 한 번만 들어간다. 화면은 이 필터 의미를 표시한다.
