# PRD

한 줄 요약: 스캐너가 찾은 CVE 중 실제로 우리 서비스 코드에 닿는 것을 가려내고, 판정 근거를 남기는 Logssey의 도달 가능성 분석 모듈이다. PoC에서 운영 api이미지의 Java CVE 14개를 판정했고, 14개 모두 `unreachable`이다.

**요약**: 스캐너가 찾은 CVE 중 실제로 우리 서비스 코드에 닿는 것을 가려내고, 판정 근거를 남기는 도달 가능성 분석 모듈이다.

## 1. 개요

코드 의존성과 컨테이너 이미지에서 알려진 CVE를 찾고, 그 CVE의 취약 코드가 우리 서비스에서 실제로 실행될 수 있는지 판정한다. 판정은 `reachable(도달 가능)` / `unreachable(도달 불가)` / `unknown(미확인)` / `not_analyzed(분석 대상 아님)` 중 하나로 표시한다. 모든 판정에는 방식과 근거를 남긴다. 확신이 없으면 `unreachable`이 아니라 `unknown`이다.

### 용어와 공통 열거값 (다섯 산출물 공통)

| 용어 | 뜻 |
|---|---|
| 스캔(Scan) | 대상 하나에 대해 SBOM 생성 → CVE 대조 → 판정까지 한 번 실행한 것 |
| 대상(Target) | 레포 커밋(`repo`, 커밋 SHA) 또는 컨테이너 이미지(`image`, digest) |
| 서비스(Service) | 레포 · ECR 리포지토리 · 클러스터 워크로드를 묶은 등록 단위(예: api). 매일 스캔과 L1이 무엇을 볼지 정한다(FR-15) |
| 구성 요소(Component) | SBOM의 패키지 하나. 키는 purl |
| 취약점(Vulnerability) | CVE 하나와 심각도, 수정 버전 |
| Finding | 대상 × 구성 요소 × 취약점 한 건. 같은 CVE라도 패키지 사본이 다르면 Finding이 다르다. 스캔끼리는 서비스·purl·CVE로 같은 Finding을 잇는다(FR-08) |
| 판정(Verdict) | Finding에 대한 Reach의 결론: 상태, 방식, 근거, 사람 검토 상태 |
| 근거(Evidence) | 판정을 뒷받침하는 것: 앱 코드의 사실(파일·줄), 호출 경로, 적용한 규칙, 메모 |
| 사실(Fact) | 앱 코드에서 수집한 관찰값(예: 컨테이너 FORM 인증 설정 여부, 역직렬화 타입의 실수형 필드) |
| 규칙(Rule) | CVE별 판정 조건. 사실과 호출 그래프 결과를 입력으로 상태를 정한다 |
| 취약 함수(Vulnerable function) | 수정으로 바뀐 메서드. 수정 커밋 diff나 취약·수정 버전 소스 diff에서 뽑는다. 호출 그래프 판정의 목표 지점 |
| 진입점(Entry point) | 호출 그래프 탐색의 시작점. 1단계 Spring 진입점(컨트롤러, @Bean, 리스너, 스케줄러 등), 2단계 모든 앱 메서드 |
| 약한 경로(Weak edge) | Object 메서드 호출·JDK 콜백처럼 근거로 약한 간선. 이것으로만 닿으면 `unknown` |
| 워크로드(Workload) | 운영 클러스터에서 실행 중인 파드·디플로이먼트와 그 imageID(digest) |
| L1 / L2 / L3 | 배포 여부 / 호출 경로 / 런타임 관측(능동/상시). 능동 관측은 스테이징·로컬·CI에서 직접 호출·테스트한 뒤, Java는 커버리지 에이전트로 취약 메서드 실행을, 네이티브는 라이브러리 로드(maps)·uprobe로 로드·호출을 확인한다(MVP, FR-14). 상시 관측은 운영 트래픽을 계속 감시하는 방식이다(비목표, 3-2) |
| 정답지(Answer key) | 사람이 도구와 독립적으로 조사해 만든 판정. 도구를 고칠 때 판정이 틀려지지 않았는지 채점하는 기준이다(M-03). 운영 중 사람 검토(`review_state`)와는 다르다 |
| 대조군 | 일부러 취약 조건을 넣은 샘플 앱이나 앱 사본. 도구가 잡는지 확인한다. 샘플 앱·대조군·회귀 테스트를 묶어 검증 세트(ARD C-14)라 부른다 |
| 게이트(Gate) | 조건에 걸리면 CI를 실패시켜 PR 머지를 막는 필수 검사. 처음에는 리포트 전용(`report_only`)으로 시작한다(FR-11) |
| 제안(확정 대기) | 사람이 조사해 낸 판정 제안이 있지만 아직 확정하지 않은 상태의 표기. 도구 판정(`status`)과 `review_state`는 그대로 두고, 그 위에 이 글자와 제안 내용을 함께 보인다. 사람이 확정하면 사람 판정과 `confirmed`가 된다. 지금은 Jackson 2.21.5 사본 7행만 해당한다(2-2) |
| 참고 사실 | 판정에 쓰지 않고 참고로만 보여주는 사실. `rules.json`에서는 `info`, API와 화면의 규칙(Rule)에서는 `info_facts`라 부른다. 근거(Evidence)에서는 `informational`로 표시한다 |
| 노이즈 감소율(M-01) | `unreachable` ÷ (`reachable` ＋ `unreachable` ＋ `unknown`). `not_analyzed`는 분모에서 빼고 판정 범위로 따로 본다. API-08의 `noise_reduction` |
| 판정 범위(M-02) | 판정한 Finding ÷ 전체 Finding. 판정한 Finding은 `status`가 `reachable`·`unreachable`·`unknown`인 것이다. API-08의 `coverage` |

| 필드 | 값 |
|---|---|
| 판정 상태 `status` | `reachable`(도달 가능) / `unreachable`(도달 불가) / `unknown`(미확인) / `not_analyzed`(분석 대상 아님: 취약 함수 데이터 없음, OS 패키지, 판정하지 않은 패키지 사본 등) |
| 분석 대상 아님 이유 `not_analyzed_reason` | `no_vuln_function_data`(취약 함수 데이터 없음) / `os_package`(OS 패키지) / `unanalyzed_copy`(판정하지 않은 패키지 사본) / `unsupported_ecosystem`(L2를 아직 지원하지 않는 생태계) |
| 판정 방식 `method` | `callgraph`(호출 그래프) / `rule`(설정·타입 규칙) / `manual`(사람) |
| 사람 검토 `review_state` | `unreviewed`(검토 전) / `provisional`(잠정) / `confirmed`(확정). 이어받은 검토를 되돌린 이유는 `reset_reason`: `verdict_changed` / `evidence_changed`(API 명세서 3-10) |
| 배포 상태 `deployment` | `running`(실행 중) / `not_running`(실행 안 함) / `unknown`(확인 못 함) |
| 심각도 `severity` | `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` / `UNKNOWN` (스캐너 값 그대로) |
| 스캔 상태 `scan_status` | `queued` / `running` / `succeeded` / `failed` |

권한 `viewer` / `reviewer` / `admin`은 서로를 포함하지 않고, 한 사람이 여러 역할을 가질 수 있다(API 명세서 2-2). API에서만 쓰는 값(스캔 `trigger`, CI 검사 `mode`·`policy` 등)은 API 명세서 3-11을 따른다.

### 1-1 판정 단계

| 단계 | 질문 | 방법 |
|---|---|---|
| L1 배포 여부 | 이 이미지가 운영에서 실행 중인가 | 실행 중 파드의 imageID(digest)와 스캔 digest를 조인하고, 이미지 revision 라벨로 커밋을 확인 |
| L2 호출 경로 | 우리 코드에서 취약 코드까지 닿나 | ① 호출 그래프: 우리 코드가 라이브러리를 부르는 경우(bcprov, jackson-core 일부)<br>② 규칙: 프레임워크가 스스로 실행하는 경우 (Tomcat 인증 설정, Spring MVC의 Jackson 역직렬화) |
| L3 실제 호출 | 런타임에 실제로 호출되나 | **능동 관측(MVP)**: 스테이징·로컬·CI에서 Java는 커버리지 에이전트로 메서드 실행, 네이티브는 라이브러리 로드(maps)·uprobe를 확인한다. 실행이 관측되면 `reachable` 근거로 쓰고, 실행되지 않았다는 것만으로 `unreachable`을 만들지 않는다(FR-14)<br>운영 상시 관측(Tetragon 등)은 비목표다(기준 PRD 3-2) |

### 1-2 실행 시점

| 시점 | SBOM | 대조 | L1 | L2 | L3 |
|---|---|---|---|---|---|
| PR | 레포 SBOM(cdxgen) | ✓ | 없음(배포 전) | ✓ 새 Finding | - |
| 이미지 빌드(ECR push 전) | 이미지 SBOM(Trivy), digest와 함께 보관 | ✓ | - | ✓ | ✓ CI 백엔드 테스트에 커버리지 에이전트를 붙여 실행 |
| 매일 | 저장된 SBOM 재사용 | ✓ 최신 DB로 재대조 | ✓ 실행 중 digest 조회 | ✓ 새 Finding | - |
| 수동 | 필요 시 | ✓ | ✓ | ✓ | ✓ 특정 API 직접 호출(`unknown` 해소, L2 후보 경로 검증) |

- SBOM은 이미지 digest당 한 번 만들고, 대조는 반복한다. 이미지는 그대로여도 취약점 DB가 매일 바뀌기 때문이다. Trivy는 CycloneDX로 출력하면 취약점 스캔을 끄므로 SBOM 생성과 대조를 두 단계로 나눈다(FR-02, FR-11).
- L3는 PR마다 돌리지 않는다. 앱을 띄우고 테스트를 돌려야 해서 무겁다. 이미지 빌드 때 기존 테스트에 에이전트만 붙여 근거를 쌓고, `unknown`이 생기면 수동으로 확인한다(FR-14).
- 미결: PR 시 cdxgen(Gradle 빌드 실행) 시간이 PR 대조에 맞는지, 매일 재판정할 때 L2 입력(bootJar)을 보관할지 실행 중 digest의 이미지에서 꺼낼지, 에이전트를 붙인 뒤 테스트 시간(지금 약 5분 49초)이 얼마나 느는지 측정이 필요하다. L1 자동화 방식은 12절 미결 사항이다.

## 2. 문제와 근거

### 2-1. 연구 근거

| 문제 | 내용 | 출처 |
|---|---|---|
| **경보 노이즈** | 스캐너가 찾는 CVE 대부분은 우리 코드에 닿지 않는다. Maven에서 취약 코드까지 호출 경로가 있는 패키지는 1% 미만이다. 모든 CVE를 같은 무게로 다루면 경보 피로로 정작 위험한 것을 놓친다. | [Mir, Keshani, Proksch (TU Delft), 2023](https://arxiv.org/abs/2301.07972) |
| **간접 의존성** | 취약한 의존성의 95%는 직접 추가하지 않은 간접 의존성이다. <br>사람이 따라가며 판단하기 어렵다. | [Endor Labs 2022](https://www.businesswire.com/news/home/20221208005272/en/Endor-Labs-Unveils-New-Research-on-Impact-of-Open-Source-Software-on-Supply-Chain-Security) |
| **수정 비용** | 모두 고치기엔 비용이 크다. 호출 경로가 있는 취약점은 9.5% 미만이다. 닿는 것부터 고치고, 나머지는 일반 유지보수 일정으로 미룰 수 있다. | [Endor Labs 2024](https://www.helpnetsecurity.com/2024/09/16/open-source-software-dependencies/) |
| **취약 함수 정보 부족** | 취약 함수를 적은 공지는 2%뿐이다. 수정 커밋을 참조하는 공지는 51%이다. 그래서 수정 커밋 diff나 취약·수정 버전 소스 diff에서 바뀐 메서드를 뽑는다(FR-09). | [Endor Labs 2024](https://www.helpnetsecurity.com/2024/09/16/open-source-software-dependencies/) |

수치는 Endor Labs 회사의 조사 기준이다.

### 2-2. 우리 데이터: 운영 api 이미지

운영에서 실행 중인 reused-api 이미지(digest `a6ffffef…`)를 스캔하면 23행이 나온다. CRITICAL 5 · HIGH 11 · MEDIUM 7이다. 23행은 Java CVE 14개, Jackson 2.21.5 사본 7행, OS 패키지 2행으로 나뉜다. PoC는 Java CVE 14개를 판정했고, **14개 모두 `unreachable`이다**.

| 묶음 | CVE | 행 | 심각도 | 판정 | 방식 |
|---|---|---|---|---|---|
| tomcat-embed-core 11.0.24 | CVE-2026-65182, 65905, 68525 | 3 | CRITICAL 3 | `unreachable` | `rule` |
| bcprov-jdk18on 1.81 | CVE-2025-14813, CVE-2026-8763, 13506, 0636 | 4 | CRITICAL 2 · HIGH 1 · MEDIUM 1 | `unreachable` | `callgraph` |
| jackson-core 3.1.5 | CVE-2026-89407, 89425 | 2 | HIGH 2 | `unreachable` | 89407 `rule`, 89425 `callgraph` |
| jackson-databind 3.1.5 | CVE-2026-68497, 91776, 91777, 19032, 83557 | 5 | HIGH 3 · MEDIUM 2 | `unreachable` | `rule` |
| Jackson 2.21.5 사본 (com.fasterxml.jackson) | 위 Jackson CVE 7개와 같음 | 7 | HIGH 5 · MEDIUM 2 | `not_analyzed`(`unanalyzed_copy`). 제안(확정 대기): 89407·89425 도달 불가, 나머지 5개 도달 불가(발동 조건 없음) | 확정되면 `manual` |
| OS 패키지 libpng, zlib | - | 2 | MEDIUM 2 | `not_analyzed`(`os_package`) | - |
| **합계** | Java CVE 14개 (CRITICAL 5 · HIGH 6 · MEDIUM 3) | **23** | **CRITICAL 5 · HIGH 11 · MEDIUM 7** | `unreachable` 14행 · `not_analyzed` 9행 | - |

이 이미지에는 도달하는 CVE가 없다. 그래서 이 절의 결과만으로는 분석기가 도달하는 경로를 실제로 잡아내는지 보여 줄 수 없다. 도달 판정 능력은 아래 실험과 샘플 앱 회귀 테스트로 따로 검증했다.

#### 읽히는 것

**문제**: SCA 결과만으로는 무엇을 고칠지 정할 수 없다.

- 경고 대부분이 실제 위험이 아니다: Trivy가 23행을 냈지만, 판정한 Java CVE 14개는 모두 도달 불가였다. 이 경고를 모두 같은 우선순위로 처리하면 팀의 대응 비용이 낭비된다. → 도달 가능성 판정(FR-05, FR-06)
- 고치는 것도 공짜가 아니다: 23행 모두 수정 버전이 있지만 버전업에는 호환성 확인이 필요하다(실험 clone에서 테스트 945개로 확인). 그래서 무엇을 먼저 고칠지 정할 근거가 필요하다. → 판정 기반 우선순위(FR-13, 시나리오 D)

**요구사항으로 이어지는 관찰**

- 패키지 수준 판정으로는 부족하다: 앱은 bcprov를 직접 부르지 않고 Spring Security의 Argon2 경로로만 쓴다. 패키지 단위로는 닿고, 메서드 단위로 봐야 배제된다(CVE-2026-13506). → 메서드 단위 호출 그래프 판정(FR-05)
- 같은 CVE가 여러 사본으로 들어온다: Jackson CVE 7개가 3.1.5와 2.21.5 두 사본에서 나온다. CVE당 한 줄로 보고하면 판정하지 않은 사본이 가려진다. → 사본별 행 표시(FR-07, US-11)
- 스캔 대상이 실제 배포물과 다를 수 있다: 10/9 로컬 이미지에는 오래된 jar 102개만 있었고 bcprov가 없었다. → 실행 중인 digest와 분석 커밋 일치 확인(FR-04)

#### 실현 가능성

- PoC 판정은 사람 판정이 확정된 CVE와 모두 일치했고, 주입 실험과 샘플 앱 회귀 테스트로 도달 경로 탐지도 확인했다. 실제 앱 (클래스 376개, jar 184개) 분석은 약 40초다. 기준은 7절(NFR-01, NFR-03), 지표는 8절(M-04~M-06)에 있다.
- 판정은 실제 배포물에 적용된다: 운영 파드 2개의 digest `a6ffffef…` 와 분석 커밋의 소스 트리가 같다.

## 3. 목표와 비목표

### 3-1. 목표

| 목표 | 뜻 | 지표 |
|---|---|---|
| **1. 닿는 것부터 가려내기** | 스캐너가 찾은 Finding마다 `reachable` / `unreachable` / `unknown` / `not_analyzed`를 정한다. 닿는 것을 먼저, 판단 못 한 것을 따로 다루게 한다. 닿지 않는 것은 지우지 않고 보류한다. | M-01, M-02 |
| **2. 근거 있는 판정** | 모든 판정에 방식과 근거를 남긴다. 앱 코드 사실은 파일·줄까지 보여준다. 사람이 확정하거나 잠정으로 기록한다. 거짓 `unreachable`을 만들지 않는다. | M-03, M-04, M-05, M-07, M-08 |
| **3. PR마다 돌릴 수 있는 속도** | 앱 1개의 L2 분석이 1분 이내다. 노트북과 CI 러너에서 돈다. | M-06 |
| **4. 실제 배포물 기준** | 판정을 실행 중인 이미지 digest와 커밋에 연결한다. 로컬 빌드물이 아니라 운영에서 도는 것을 판정한다. | M-09 |

### 3-2. 비목표

| 하지 않는 것 | 이유 | 대신 하는 것 |
|---|---|---|
| 스캐너·취약점 DB 직접 개발 | 성숙한 OSS가 있다. 재발명하지 않는다 | Trivy, Grype, cdxgen을 조합하고, 직접 만드는 부분은 연결·판정으로 한정한다 |
| 우리 코드 자체의 취약점 분석(SAST) 직접 구현 | 이미 도구가 많다 | 확장 단계에서 Semgrep CE 같은 기존 도구 결과를 공통 Finding으로 받아 같은 화면에 보여주는 것을 검토한다 |
| 자동 수정, 자동 PR | 업그레이드 적용은 팀이 결정한다. 호환성 확인이 필요하다 | 최소 수정 버전, 패치, 실험용 clone의 테스트 결과를 제안까지만 한다(FR-13) |
| 최종 판정에 AI 사용 | 정답이 DB와 코드에 있어 규칙이 더 정확하다. AI 결과는 재현할 수 없다 | AI는 취약 함수 후보 생성, 구성요소 식별 후보(FR-02), 판정 설명에만 쓴다. 후보는 사람이 확인한 것만 쓴다. AI에 보내는 데이터 범위는 ARD SR-11이 정한다(NFR-04) |
| 결과에서 CVE 지우기 | 닿지 않는다는 판정도 틀릴 수 있고, 근거를 남겨야 검토할 수 있다 | `unreachable`과 `not_analyzed`도 목록에 남긴다. 도달 불가는 삭제가 아니라 보류다 |
| Logssey의 다른 모듈(시크릿, IaC, CSPM, IAM, 런타임 탐지) | 다른 담당의 범위다 | 공통 Finding과 자산 연결 키(digest, 레포·커밋, purl)로 접점만 맞춘다 |
| L3 상시 관측(운영 트래픽 감시) | 운영 부하와 인프라 비용이 크고, 관찰 기간에 안 쓰인 코드를 "안 쓰임"으로 오판할 수 있다 | L3 능동 관측(FR-14): 스테이징·로컬·CI에서 직접 호출·테스트 후 Java는 커버리지 에이전트, 네이티브는 라이브러리 로드(maps)·uprobe로 확인. 실행되면 `reachable` 근거, 실행 안 됨은 `unreachable` 근거로 쓰지 않음 |
| 대용량 DB에 기대는 패키지 수준 도구 | dep-scan은 DB가 약 42GB라 노트북에서 실패했다. 패키지 수준 판정은 bcprov 같은 경우를 위험으로 남긴다 | 함수 수준 판정을 직접 조립한다(NFR-06) |

## 5. 사용 시나리오와 사용자 스토리

### 5-1. 사용 시나리오

| 시나리오 | 흐름 | 관련 US |
|---|---|---|
| **A. PR에 새 CVE가 들어올 때** | 개발자가 의존성을 바꾼 PR을 올린다 → CI가 SBOM을 만들고 CVE를 대조한다 → 새로 생긴 Finding을 판정한다 → PR 결과에 상태별 개수와 상세 링크를 남긴다(리포트 전용, 빌드는 깨지 않음) → `reachable`이나 `unknown`이 있으면 보안 담당자가 검토한다 | US-04, US-02, US-03 |
| **B. 운영 이미지 정기 점검** | 하루 1번 실행 → 실행 중 워크로드의 digest를 조회한다(L1) → 저장된 SBOM을 최신 DB로 다시 대조한다 → 새 Finding을 판정한다 → 요약을 갱신하고 새 Finding을 따로 표시한다 | US-06, US-10, US-09 |
| **C. 판정 근거 검토와 확정** | 보안 담당자가 `unreviewed` Finding을 거른다 → 상세에서 앱 코드 사실(파일·줄), 적용 규칙, 후보 경로를 본다 → 필요하면 소스를 직접 확인한다 → `confirmed` 또는 `provisional`과 메모를 남긴다 | US-02, US-03, US-11 |
| **D. 업그레이드 우선순위 결정** | Finding 목록을 기본 정렬(`reachable` → `unknown` → `unreachable` → `not_analyzed`, 같은 상태 안에서는 심각도 → CVE 순)로 보고, `deployment`를 함께 본다 → 라이브러리별 최소 수정 버전과 실험 결과를 확인한다 → 팀이 적용 여부를 정한다. Reach는 PR을 만들지 않는다 | US-05, US-01 |
| **E. 새 CVE 규칙 추가** | 규칙 작성자가 수정 커밋 diff나 버전 diff에서 취약 함수를 정한다 → 조사 파일을 쓰고 생성 스크립트로 데이터를 만든다 → 필요하면 규칙을 추가한다 → 대조군에서 `reachable` 또는 `unknown`이 나오는지 확인한다 → 회귀 테스트가 모두 통과하면 반영한다 | US-08 |

업계 공통 원칙(Sonatype): 도달 가능은 우선 처리, 도달 불가는 삭제가 아니라 보류, 판단 불가는 따로 조사한다. 시나리오 D는 이 원칙을 따른다.

### FR-01 스캔 실행

대상은 레포 커밋(`repo` , 커밋 SHA) 또는 컨테이너 이미지(`image` , digest)다. 스캔 한 번은 SBOM 생성 → CVE 대조 → 판정까지 실행한다. 어떤 서비스를 스캔할지는 FR-15의 등록 목록이 정한다.

#### 수용 기준

1. 이미지 대상은 digest로 기록한다. 태그로 요청하면 digest로 확정한 뒤 기록한다(ECR 태그는 MUTABLE 이라 태그만으로는 내용이 확정되지 않는다).
2. 스캔은 `scan_status` 를 `queued` → `running` → `succeeded` 또는 `failed` 로 남긴다. 실패하면 실패한 단계와 이유를 남긴다.
3. 스캔 결과에 대상, 분석한 jar의 sha256, 스캐너 버전, 취약점 DB 날짜를 남긴다.
4. 같은 대상의 스캔 이력을 남기고, 이전 스캔과 Finding 차이를 비교할 수 있다.

### FR-02 SBOM 생성

이미지와 레포에서 CycloneDX SBOM을 만든다. 구성 요소의 키는 purl이다. 지금 쓰는 도구는 이미지는 Trivy, 레포는 cdxgen이다. cdxgen은 Gradle 빌드를 실행해 간접 의존성까지 잡는다. 도구는 아래 기준을 만족하면 바꿀 수 있다.

#### 수용 기준

1. 이미지 SBOM은 이미지 안 `BOOT-INF/lib` jar의 99% 이상을 좌표(group·artifact·version)까지 맞힌다(10/7 Trivy: 182/184).
2. 레포 SBOM은 `gradle.lockfile` 이 없어도 Gradle `runtimeClasspath` 의 간접 의존성을 모두 포함한다(10/7 cdxgen: 266/266).
3. 이미지 SBOM과 레포 SBOM의 좌표가 다르면 레포 SBOM(빌드 도구가 해석한 좌표)을 우선하고, 차이를 결과에 기록한다.
4. 버전이 범위로만 적힌 경우 (`≥`, `^`, `1.+` 등)는 잠금 파일이나 의존성 해석기로 먼저 확정한다. 확정하지 못하면 “버전 미확정”으로 두고 범위 전체를 기준으로 대조한다.
5. 결정적 방법(`pom.properties` , MANIFEST, SHA-1 조회, 레포SBOM 교차 확인)으로 식별하지 못한 구성요소만 AI로 후보를 만든다. AI 후보에는 출처와 신뢰도를 남기고(CycloneDX `evidence.identity` 또는 `properties` ), 사람이 확인하기 전에는 “구성요소 추정”으로 표시한다. 추정 구성요소의 Finding은 `unreachable` 로 확정하지 않는다(NFR-01). AI에 보내는 데이터는 패키지·클래스 이름, jar 안 경로, 버전 문자열로 한정하고, 분석 대상에서 온 문자열은 지시가 아닌 데이터로 다룬다(ARD SR-11).
6. SBOM에 만든 도구와 버전을 남긴다. AI 후보는 입력(jar SHA-1 등) 기준으로 저장해 재사용 하고, 모델·프롬프트 버전을 남긴다(NFR-04, NFR-05).
7. SBOM을 대상과 함께 저장해, 재빌드 없이 다시 대조할 수 있게 한다(FR-11의 하루 1번 재대조, ARD C-13).
8. 못 보는 범위를 결과에 한계로 적는다. 프론트 번들 안의 JS라이브러리, relocation된 shading 코드(AWS SDK `third-party-jackson-core` ), JRE 안에 정적으로 포함된 네이티브 라이브러리다. JRE 자체도 Trivy SBOM에는 없다(10/7 비교에서 Syft만 찾음). 앞의 두 가지는 수용 기준 5의 AI후보 대상이고, JRE는 Syft 보완을 확장 단계에서 검토한다.

### FR-03 CVE 대조

같은 SBOM을 Trivy와 Grype로 대조하고 purl 기준으로 합친다.

Finding은 대상 x 구성요소 x 취약점 한 건이다.

#### 수용 기준

1. 두 도구(Trivy, Grype)의 결과를 purl과 CVE ID로 합친다. 한쪽에만 있는 행은 어느 도구가 찾았는지 표시한다.
2. 같은 CVE라도 패키지 사본이 다르면 Finding을 따로 만든다(예: jackson-core 3.1.5와 2.21.5).
3. 심각도는 스캐너 값을 그대로 쓴다. 다른 출처와 다르면 메모로 남긴다(예: CVE-2025-14813은 Trivy가 CRITICAL, CNA CVSS 벡터는 7.5).
4. Finding마다 설치 버전과 수정 버전을 남긴다.

### FR-04 L1 배포 여부

실행 중 파드의 imageID(digest)와 스캔 digest를 조인한다. 이미지 revision 라벨 (`org.opencontainers.image.revision` )로 배포 커밋을 찾고 분석 커밋과 비교한다.

#### 수용 기준

1. 실행 중 워크로드마다 digest, 파드 수, 연결된 스캔을 보여준다.
2. Finding마다 `deployment` 를 `running` / `not_running` / `unknown` 으로 표시한다. 클러스터를 조회하지 못하면 `unknown` 이다. `not_running`으로 추정하지 않는다.
3. 배포 커밋과 분석 커밋이 다르면 소스 트리가 같은지 비교해 결과를 남긴다.
4. 클러스터 조회는 읽기 전용 권한만 쓴다(NFR-05).

### FR-05 L2 호출 그래프 판정

bootJar 바이트 코드로 호출 그래프를 만든다(RTA). 진입점은 2단계이다. 1단계는 Spring 진입점(컨트롤러, @Bean, 리스너, 스케줄러 등) 이고, 2단계는 모든 앱 메서드다. Object 메서드 호출과 JDK 콜백은 약한 경로로 분리한다.

#### 수용 기준

1. 취약 함수 데이터가 있는 Finding마다 진입점에서 취약 함수까지 경로 유무를 판정한다.
2. 1단계 진입점에서 닿으면 그 진입점(예: 컨트롤러 메서드)부터의 경로를 근거로 보여준다.
3. 약한 경로로만 닿으면 `unknown`이다.
4. 취약 메서드가 분석한 jar에 없으면 `unknown`이다. 못 찾았다고 `unreachable`로 판정하지 않는다.
5. 호출 경로에는 “가장 짧은 후보 경로이며 실제 경로와 다를 수 있다”를 표시한다.

### FR-06 L2 규칙 판정

프레임워크가 스스로 실행하는 경로(Tomcat 인증기, Spring MVC의 Jackson 역직렬화)는 우리 코드 기준 호출 그래프에 나오지 않는다. 그래서 앱 코드에서 사실을 모으고 CVE별 규칙으로 판정한다. 규칙 형식과 내용은 규칙명세서(GR, F-, RULE-)가 정한다.

#### 수용 기준

1. 사실은 앱 코드에서만 수집한다. 사실마다 파일·줄을 남긴다.
2. 규칙은 도달 가능 → 도달 불가 조건 → 미확인 조건 → 기본값 순서로 평가한다.
3. 역직렬화 타입은 요청 본문(@RequestBody 등), 리스너 파라미터, readValue 계열, TypeReference, HTTP 클라이언트 응답 타입에서 시작해 필드 타입을 따라간다.
4. 판정에 쓰지 않는 참고 사실은 판정 근거와 구분해 보여준다.
5. 규칙 판정이 호출 그래프 결과와 달라 보이면 이유를 붙인다(과대근사, 또는 프레임워크가 실행하는 코드).

### FR-07 판정 결과·근거 출력

판정 결과를 JSON과 Markdown 보고서로 낸다. 앱 코드 사실을 먼저 보여주고, 호출 경로는 후보로 표시한다. 같은 CVE라도 다른 사본은 별도 행이다.

#### 수용 기준

1. Finding마다 `status` , `method` , 근거, `review_state` 를 출력한다.
2. `unreachable` 과 `not_analyzed` 도 지우지 않고 출력한다. `not_analyzed` 에는 이유(취약 함수 데이터 없음, OS 패키지, 판정하지 않은 사본)를 붙인다.
3. 판정 행은 판정한 패키지의 설치·수정 버전을 쓴다.
4. `unreachable` 근거에는 확인했지만 없던 것을 적는다(예: FORM 인증 설정 없음).
5. 보고서 머리말에 대상, 분석한 jar, 상태별 개수를 쓴다.

### FR-08 사람 검토

보안 담당자가 도구 판정의 근거를 보고, Finding 마다 검토 상태( `unreviewed` / `provisional` / `confirmed`)와 메모를 남긴다. `unreachable` 은 고치지 않고 보류하므로 같은 Finding이 매일 재대조와 새 빌드마다 다시 나온다. 그래서 검토 상태는 다음 스캔으로 이어받고, 판정 근거가 바뀌면 다시 검토한다. 사람 판정이 도구와 다르면 그 사례를 검증 세트(ARD C-14)에 추가한다. 도구의 정확도는 운영 검토가 아니라, 도구와 독립적으로 만든 정답지와 검증 세트로 잰다(M-03, M-04). 운영 검토는 도구가 보여 준 근거를 보고 판단하므로 도구 쪽으로 치우치기 쉽기 때문이다.

#### 수용 기준

1. `review_state` 는 `unreviewed` / `provisional` / `confirmed` 다. 새 Finding은 `unreviewed` 로 시작한다.
2. 검토 기록에 검토자, 시각, 사람 판정, 메모를 남긴다.
3. 사람 판정이 도구 판정과 다르면 두 판정을 모두 남기고 불일치로 표시한다. 불일치 Finding을 따로 거를 수 있다.
4. 도구가 판정하지 못한 Finding(`not_analyzed`)을 사람이 판정하면 `method` 는 `manual` 이다.
5. 검토 기록은 `reviewer` 권한이 있어야 쓸 수 있다.
6. 사람이 확정하기 전의 판정 제안은 `status` 와 `review_state` 를 바꾸지 않는다. “제안(확정 대기)”과 제안 내용을 함께 보인다.
7. 같은 Finding(같은 서비스의 같은 purl·CVE)이 다음 스캔에 다시 나오면 검토 상태와 메모를 이어받는다.
8. 도구 판정(`status`)이나 판정 근거(사실, 호출 경로, 적용 규칙)가 바뀌면 이어받은 검토 상태를 `unreviewed` 로 되돌리고, 이전 검토 기록은 이력으로 남긴다.
9. 사람 판정이 도구 판정과 다른 Finding은 검증 세트(ARD C-14)에 추가할 후보로 표시한다.

### FR-09 취약 함수 데이터 관리

수정 커밋 diff나 취약·수정 버전 소스 diff에서 바뀐 메서드를 취약 함수로 정한다. 조사 파일을 쓰고, 생성 스크립트(`make_spec.py`)로 `vuln-functions.json`을 만든다.

#### 수용 기준

1. 취약 함수마다 출처(수정 커밋 diff 또는 버전 diff)와 확인 방법(취약 버전 jar에서 `javap` 로 시그니처 확인)을 남긴다.
2. 데이터 파일은 조사 파일에서 생성 스크립트로만 만든다. 데이터 파일을 직접 고치지 않는다.
3. 넣으면 오탐이 나는 메서드는 빼고 이유를 남긴다(예: 13506에서 일반 파싱과 공유하는 `ASN1InputStream.buildObject`).
4. 취약 함수 데이터가 없는 CVE의 Finding은 `not_analyzed` 로 남긴다. `unreachable` 로 판정하지 않는다.
5. AI는 후보를 만드는 데만 쓴다. 사람이 확인한 것만 데이터에 넣는다. AI에는 공개 공지와 수정 커밋만 보내고, 우리 앱 소스 코드는 보내지 않는다(ARD SR-11).

### FR-10 공통 Finding 내보내기 (OCSF)

Finding을 Logssey 공통 Finding(OCSF)으로 내보낸다.

#### 수용 기준

1. 스캔 하나의 Finding을 OCSF 형식으로 내보낸다(API-11).
2. `status` , `method` , `review_state` , `deployment` , 근거 요약이 빠지지 않는다.
3. 자산 연결 키로 이미지 digest, 레포·커밋, purl을 넣는다.
4. 내보낸 결과에 스키마 버전을 적는다.

### FR-11 CI 연동

GitHub Actions 트리거 3종으로 돈다. PR마다 빠른 대조(`pull_request`), 하루 1번 저장된 SBOM 재대조와 재판정(`schedule`), 수동 실행(`workflow_dispatch`)이다. 여기에 배포 파이프라인의 이미지 빌드 단계(ECR push 전)가 더해진다. 시점별로 하는 일은 아래와 같다.

| 시점 | SBOM | 대조 | L1 | L2 | L3 |
|---|---|---|---|---|---|
| PR | 레포 SBOM(cdxgen) | ✓ | 없음(배포 전) | ✓ 새 Finding | 없음 |
| 이미지 빌드(ECR push 전) | 이미지 SBOM(Trivy), digest와 함께 보관 | ✓ | 없음 | ✓ | ✓ 백엔드 테스트에 커버리지 에이전트를 붙여 실행 (FR-14) |
| 매일(`schedule`) | 저장된 SBOM 재사용 | ✓ 최신 DB로 재대조 | ✓ 실행 중 digest 조회<br>(FR-04) | ✓ 새 Finding | 없음 |
| 수동<br>(`workflow_dispatch`) | 필요 시 | ✓ | ✓ | ✓ | ✓ 특정 API 직접 호출 (`unknown` 해소, <br>L2 후보 경로 검증) |

SBOM은 이미지 digest당 한 번 만들고 대조는 반복한다. 이미지는 그대로여도 취약점 DB가 매일 바뀌기 때문이다. L3는 앱을 띄우고 테스트를 돌려야 해서 PR마다 돌리지 않는다.

**게이트 전환** (ARD Q-07, AD-17)

게이트는 조건에 걸리면 CI를 실패시켜 PR 머지를 막는 필수 검사다. 처음부터 막으면 오탐 하나가 개발을 멈추므로, 리포트 전용(`report_only`)으로 시작해 아래 기준을 만족하면 게이트(`gate`)로 바꾼다.

- 대상: PR에서 새로 생긴 Finding(기준 스캔에 없던 purl × CVE)만 본다. 이미 있던 Finding 때문에 PR을 막지 않는다.
- 조건: API 명세서 6-2를 따른다. `reachable`이면서 CRITICAL·HIGH면 실패, `reachable` MEDIUM 이하·`unknown`·CRITICAL·HIGH인 `not_analyzed`는 경고, 그 밖의 것은 통과다. `unreachable`은 막지 않는다(보류 원칙).
- 전환 기준(제안): 리포트 전용으로 4주 이상 운영하고, 그 기간 `reachable` 판정 중 사람 검토에서 오탐으로 확인된 것이 0건이며, 경고에 걸린 Finding이 모두 검토됐을 때 팀이 전환을 정한다.
- 예외: 실패한 PR이라도 `reviewer` 권한자가 사유와 만료일을 남기면 통과시킬 수 있다. PR 작성자 본인은 승인할 수 없다(ARD SR-10). 예외는 그 Finding의 검토 기록에 남고, 만료되면 다시 게이트 대상이 된다.
- 되돌리기: 전환 뒤 오탐으로 머지가 막히면 그 조건만 경고로 내리고, 사례를 검증 세트(ARD C-14)에 추가한다.

#### 수용 기준

1. PR마다 새로 생긴 Finding과 판정을 PR 결과로 보여준다.
2. 처음에는 리포트 전용이다. 결과와 관계없이 빌드를 깨지 않는다. 게이트로 바꿀 때는 위 "게이트 전환"의 대상·조건·전환 기준·예외·되돌리기를 따른다.
3. 하루 1번 저장된 SBOM을 최신 DB로 다시 대조하고, 새 Finding을 판정한다.
4. 수동 실행을 지원한다.
5. 재사용 워크플로(`workflow_call`)로 한 번 정의하고, 레포마다 호출한다.
6. 이미지 스캔은 ECR push 전에 한다.
7. 이미지 빌드 단계의 백엔드 테스트는 커버리지 에이전트를 붙여 실행하고, 결과를 L3 근거로 남긴다(FR-14). PR 단계에서는 L3를 돌리지 않는다.

### FR-12 대시보드

요약, Finding 목록·상세, 워크로드를 보여준다. 화면 구성은 화면 명세서(SCR-01~06)가 정한다.

#### 수용 기준

1. 요약(SCR-01)에 상태별·심각도별 개수, 노이즈 감소율(M-01), 판정 범위(M-02)를 보여준다. 두 지표는 분수로 보인다(PoC: 14/14,14/23).
2. Finding 목록(SCR-02)은 `status`, `severity`, 대상, `deployment`, `review_state`, 패키지로 거를 수 있다. 도구 판정과 사람 판정이 다른 Finding(FR-08)과 새 Finding(US-10)도 따로 거를 수 있다.
3. 기본 목록에서 `unreachable`과 `not_analyzed`를 숨기지 않는다.
4. 상태·방식·검토 표시는 1절의 공통 열거값을 그대로 쓴다.
5. 요약 숫자는 목록을 같은 조건으로 거른 개수와 같다.

### FR-13 업그레이드 제안

Finding마다 최소 수정 버전을 보여주고, 라이브러리 단위로 패치와 테스트 결과를 제안한다. 적용 여부는 팀이 결정한다.

#### 수용 기준

1. Finding마다 스캐너가 알려준 수정 버전을 보여준다.
2. 같은 라이브러리의 Finding을 모두 없애는 최소 버전을 계산한다(예: bcprov는 CRITICAL 2개를 모두 없애려면 1.85 이상).
3. 버전을 정하는 위치를 알려준다(예: Spring Boot가 관리하는 Tomcat·Jackson 3은 관리 버전을 덮어써야 한다).
4. 패치와 테스트 결과는 실험용 clone에서 만든 것만 첨부한다. 실제 레포에는 쓰지 않는다.
5. `unreachable`이어도 일반 유지보수 일정에 넣도록 표시한다.

### FR-14 L3 능동 관측

스테이징, 로컬, CI 러너에서 커버리지 에이전트(예: JaCoCo)를 붙여 앱을 띄우고, 특정 API를 직접 호출하거나 기존 테스트를 돌려 취약 메서드(`vuln-functions.json`)가 실행됐는지 확인한다. 계측 범위는 라이브러리 패키지 `org.bouncycastle.*`, `tools.jackson.*`, `com.fasterxml.jackson.*`, `org.apache.catalina.*`까지다. 공격 페이로드는 필요 없고, 취약 메서드까지 가는 정상 입력이면 된다. 네이티브 라이브러리(OS 패키지, 예: libpng·zlib)는 두 단계로 본다. ① 라이브러리 로드 확인: API·테스트 실행 후 `/proc/<java-pid>/maps`에서 해당 .so가 올라왔는지 본다. ② 함수 호출까지 볼 때만 bpftrace·perf uprobe로 공개 함수(예: `inflate`, `png_read_info`)에 건다. root 권한이 필요하고, Alpine 라이브러리는 공개 심볼만 걸 수 있다. Java 메서드 실행은 커널 수준 도구(Tetragon)로 볼 수 없어, Java는 커버리지 에이전트, 네이티브는 maps·uprobe로 본다. 운영에서는 실행하지 않는다. 운영 트래픽을 계속 감시하는 상시 관측은 비목표다(3-2). Tetragon은 상시 관측과 함께 확장 단계로 보류한다.

#### 실행 시점

1. 이미지 빌드 시(기본): CI에서 백엔드 테스트를 커버리지 에이전트와 함께 실행해, 빌드마다 근거를 쌓는다(FR-11). 별도 환경 없이 기존 테스트에 에이전트만 붙인다.
2. 필요할 때(수동): `unknown`이 생기거나 L2 후보 경로를 검증할 때, 스테이징이나 로컬에서 특정 API를 직접 호출한다.
3. PR마다는 돌리지 않는다. 앱을 띄우고 테스트를 돌려야 해서 무겁다.

#### 목적

1. `unknown` 해소: 실행이 관측되면 `reachable`로 올린다.
2. L2 후보 경로 검증: 호출 그래프가 낸 후보 경로가 실제로 실행되는지 확인한다.
3. 규칙 대조군 확인: 규칙의 '도달 가능' 대조군이 실제로 실행되는지 확인한다.

#### 수용 기준

1. 실행이 관측되면 `reachable` 근거로 쓴다. Java는 메서드 단위 커버리지, 네이티브는 라이브러리 로드(maps)나 공개 함수 호출(uprobe)로 본다.
2. 관찰 기간에 로드·호출되지 않았다는 것만으로 `unreachable`을 만들지 않는다.
3. 관측 근거에 빌드(jar sha256 또는 이미지 digest), 설정(환경 변수·프로필의 키 이름과 켜짐 여부, 값은 기록하지 않음), 호출한 API·테스트 목록, 확인 방법(coverage / maps / uprobe), 관측 시각을 함께 기록한다. 스테이징 설정이 운영과 다르면 결과가 달라질 수 있기 때문이다(예: LLM 공급자 `anthropic` 설정에 따라 Jackson 2 경로가 생김).

### FR-15 대상(서비스) 관리

서비스 하나를 레포, ECR 리포지토리, 클러스터 워크로드로 묶어 등록한다. 매일 스캔과 L1 조회가 무엇을 볼지는 이 목록이 정한다. 스캔(FR-01)은 실행할 때마다 생기는 단위이고, 대상 등록은 한 번 등록해 계속 유지하는 단위라서 따로 둔다.

#### 수용 기준

1. 서비스마다 레포, ECR 리포지토리, 클러스터 워크로드(네임스페이스, 디플로이먼트)를 묶어 등록한다(예: api = `service-backend` ↔ `logssey/reused-api` ↔ 운영 reused-api 워크로드).
2. 매일 스캔과 L1 조회는 등록된 서비스 목록을 기준으로 한다.
3. 클러스터에 등록되지 않은 워크로드가 있으면 "미등록"으로 표시한다. 등록하지 않은 서비스가 감시에서 조용히 빠지지 않게 하기 위해서다.
4. MVP는 레포에 커밋한 설정 파일로 관리한다. 등록 API와 화면은 확장 단계다.
