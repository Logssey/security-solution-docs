# 공통 리포트 "취약점(이미지·공급망)" 장

**한 줄 요약**: 대시보드 공통 리포트(파트마다 장을 넘기는 보고서)에 Reach가 넘기는 장의 내용이다. 운영에서 실행 중인 이미지의 Finding을 넘기고, 위험도는 스캐너 심각도 그대로, 도달 판정은 리포트에 넣을지만 정한다. 도달 불가는 목록에서 빼고 "보류"로 따로 센다.

- 구현: dashboard-backend `com.logssey.reach.report.ReachReportChapterProvider` (공통 리포트 `ReportChapterProvider`, 파트 `VULNERABILITY`). 조회는 `ReachQueryService.reportScope`
- 화면: 취약점 관리 요약의 [리포트 만들기] → 공통 리포트 새로 만들기(파트 선택 = 취약점)
- 기준일: 2026-11-24

## 1. 범위

| 항목 | 기준 | 이유 |
|---|---|---|
| 대상 | 기본 범위(API-08 `basis=RUNNING`)의 **이미지 대상만**. L1 조회가 48시간 넘게 없으면 앱마다 최신 이미지(LATEST) | 리포트는 "지금 운영에 있는 것"을 말한다 |
| 빼는 것 | 레포 대상 스캔, PR 검사 | 레포 대상은 배포 여부를 알 수 없고 이미지와 겹친다. PR 검사는 머지 전 가정 상태다. 이미지 스캔 없이 레포만 있는 앱은 범위 표에 이름만 |
| 같은 것 | 같은 앱·패키지 이름·버전·CVE는 한 건 | 배포 중 실행 중 digest가 둘이면 둘 다 범위에 든다. 이름이 같아도 버전이 다르면(Jackson 2.x 사본과 3.x) 다른 jar라 따로 센다 |

## 2. 판정과 위험도

- **리포트가 쓰는 판정**: 사람이 확정(`CONFIRMED`)했으면 사람 판정, 잠정(`PROVISIONAL`)이면 도구 판정과 비교해 위험한 쪽(순위 `REACHABLE` > `UNKNOWN` = `NOT_ANALYZED` > `UNREACHABLE`, NFR-01), 아니면 도구 판정
- **넣는 것**: 도달 가능·확인 못 함·판정 전(`NOT_ANALYZED`, 판정 데이터 없음 등). 판정 전을 빼면 판정 데이터가 없는 CRITICAL이 보고에서 사라진다
- **보류**: 도달 불가는 findings에서 빼고 범위 표 "도달 불가로 보류"에 "사람 확정 a · 검토 전 b (심각도별)"로 센다. 지우지 않는다(GR-02). 검토 전 건수를 따로 보여 PRD M-08("최종 보고의 판정은 사람 확정")과의 차이를 드러낸다
- **위험도**: 스캐너(Trivy·Grype) 심각도 그대로. `UNKNOWN`은 공통 리포트의 `UNASSESSED`(미평가, 기한·우선순위에서 빠짐). 도달 판정으로 등급을 올리거나 내리지 않는다

## 3. Finding 한 건

| 칸 | 값 |
|---|---|
| id | `REACH-F<finding_id>` |
| 제목 | `<CVE> · <패키지> <버전>: <설명>`. 설명은 판정한 건이면 영향 기능(판정 데이터의 한국어 요약), 판정 전이면 같은 CVE의 판정 데이터 한국어 요약(판정 데이터가 다른 패키지에만 있는 사본도 같은 취약점이라, 예: Jackson 2 사본에 Jackson 3 데이터의 요약), 판정 데이터에 없는 CVE면 권고문 제목(영어일 수 있음). 권고문 제목 앞에 붙은 패키지 좌표(`com.fasterxml.jackson.core/jackson-databind: …`)는 뗀다. 설명은 60자에서 자른다 |
| 위험도 | 2절 |
| 대응 | 공통 상태 "미조치"와 판정: `미조치 · 도달 가능`(사람 확정이면 "(사람 확정)", 도구 판정이 L3로 올라 도달 가능이면 "(L3 실행 확인)"), `미조치 · 확인 못 함 (사람 검토 필요)`, `미조치 · 판정 전`(사유는 근거 칸에). Reach에는 조치 상태가 없다 |
| 자산 | `<앱> 운영 이미지 (<대상 표시 이름>)`. 실행 중이 아니면 `<앱> 최신 이미지 (실행 확인 안 됨, …)` |
| 위치 | `<패키지>@<버전>` (이미지 안 jar 경로) |
| 근거 | 사람 확정·잠정 판정, 판정 전이면 `판정 전: <사유>`(판정 데이터 없음: "이 CVE의 판정 데이터가 아직 없음", 사본: "같은 CVE의 판정 데이터가 다른 패키지에만 있어 이 패키지는 아직 판정하지 않음", OS 패키지·지원하지 않는 언어도 문장으로), 도구 판정과 방식(호출 그래프·규칙)과 규칙 설명(why_ko) 앞부분(L3가 올린 판정이면 서버가 붙인 L3 문장을 떼고 L2 판정의 이유), L3: 실행으로 판정을 올렸으면 "실제 실행으로 판정을 올림"(구간 실행이든 함수만 실행이든), 올리지 않았는데 구간이 실행됐으면 "취약 구간 실행됨 (판정은 그대로)"(규칙 데이터 `l3` 한도 때문이거나 이미 도달 가능) |
| 발견일 | 같은 앱·패키지·CVE가 이미지 대상에 처음 나온 때(PR이 아닌 스캔의 도구 판정이 있는 Finding 중 가장 이른 `first_seen_at`). digest가 바뀌면 Finding이 새로 생기므로, 그대로 쓰면 대응 기한이 배포마다 다시 시작한다 |
| 기한 | 공통 기본값(발견일 + 심각도별 일수) |
| 담당 | `미지정` |
| 조치 | 아래 4절 조치 제목 그대로(공통 리포트가 이 제목으로 조치에 묶는다) |

**넣지 않는 것** (Finding 칸은 공통 리포트의 AI 조치 방안 요청에도 쓰인다): 검토 메모, 사람 판정 요약(메모 앞부분), 검토자 이름, 근거 줄의 설정·소스 원문, 호출 경로, L3 설정 값, 레지스트리 주소(계정 ID)·클러스터·네임스페이스·워크로드 이름(개수만), CI 요청 주체.

## 4. 조치 방안

Finding을 조치 제목으로 묶고 Critical·High가 많은 순서로 둔다.

| 경우 | 제목 | 방법 |
|---|---|---|
| 수정 버전이 있음 | `<이름> <버전> 이상으로 올리기` | Spring Boot가 버전을 정하는 라이브러리(아래 묶음)면 그 버전을 담은 Spring Boot 패치로 올리고, 없으면 빌드 파일의 버전 속성으로 고정. 그 밖은 빌드 파일의 의존성 버전(다른 라이브러리가 끌어온 것이면 그 라이브러리)을 올리기 |
| OS 패키지 | `베이스 이미지 갱신` | 베이스 이미지 digest를 새로 받고 OS 패키지 갱신 |
| 수정 버전 없음 | `<패키지> 수정 버전 없음: 완화책 검토` | 권고문의 완화책 적용, 수정 버전이 나오면 올리기 |

- **묶음**: Spring Boot 버전 속성 하나로 같이 올라가는 jar는 조치 하나다. `tomcat-embed-*` → 이름 `Tomcat`(속성 `tomcat.version`), `jackson-*` 2.x → `Jackson`(`jackson-2-bom.version`), 3.x → `Jackson`(`jackson-bom.version`). 그 밖은 패키지마다(앱·이름·버전)
- **올릴 버전**: Finding마다 설치 버전과 앞 두 숫자가 같은 수정 버전(없으면 설치 버전보다 큰 것 중 가장 작은 것)을 고르고, 묶음 안에서 **가장 높은 것**. 도달 불가로 보류한 건도 넣는다 — 어차피 올리는 김에 보류한 Critical까지 고치는 버전을 권한다(Re:Used api: 넣는 Tomcat 2건은 11.0.26이면 되지만 보류한 Critical 3건이 11.0.27에서 고쳐져 11.0.27)
- **영향 칸**: `Critical a · High b · 그 밖 c건 (<앱>)`, 같은 조치로 고쳐지는 보류 건이 있으면 `· 도달 불가로 보류한 n건도 함께 해소`
- **보류 건만 있는 묶음**은 조치 목록에 없고 범위 표 "보류 건만 있는 패키지 (다음 정기 업데이트 때 올리기)"에 `<이름> <설치 버전> → <올릴 버전> (n건)`으로 적는다

## 5. 장의 나머지 칸

| 칸 | 값 |
|---|---|
| 핵심 숫자 | 도달 가능 Critical·High 건수 |
| 요약 문장 | `운영 이미지에서 도달 가능 Critical·High N건 · 확인 못 함 M건 (도달 불가 K건 보류)` |
| 세는 단위 | 운영 이미지의 패키지×CVE (도달 불가 제외) |
| 위험도 분포 | findings와 같은 집합 |
| 범위 표 | 기준(실행 중 / 최신), 대상 이미지(표시 이름), 판정 범위(판정 a / 전체 b, 판정 전 c), 도달 불가 보류, 보류 건만 있는 패키지(4절), 실행 중인데 스캔 결과가 없는 이미지 수, 이미지 스캔이 없는 앱 |
| 기준 시각 | 범위 이미지 스캔이 끝난 시각 중 **가장 이른 것**(재대조 한 번이 실패해도 오래됐다고 보이게) |
| 신규 | findings 중 발견일이 보고 기간 안 |
| 해결 | 아직 세지 않는다(빈칸). 해결 = "운영 이미지에서 사라짐"을 재대조 기록으로 세는 방법은 다음에 |
| 링크 | 취약점 요약, 도달 가능·확인 못 함 목록(실행 중 이미지), 판정 규칙 |
| 판단 기준 | 1~4절을 다섯 줄로 |
| 메모 | 실행 중 기준을 못 썼을 때, 스캔 결과가 없는 실행 중 이미지가 있을 때 |

## 6. 공통 리포트에 물어볼 것

- 대응 상태 공통 이름(미조치·조치 중·재검사 대기·해결·예외 승인)의 매핑 기준. "고친 이미지가 빌드됐고 배포 대기"를 "조치 중"으로 써도 되는지
- 보류·예외 승인 건을 기한 초과·우선순위 계산에서 빼 주는 공통 칸이 필요한지(지금은 상태와 상관없이 모든 Finding을 센다)
- Finding 건수 상한(인쇄본에 표 전체가 들어간다)
